## 運用ルール

- 各書籍で同じ背景説明や定義を繰り返し書かず、このファイルに抽出する
- 書籍本文では、共通説明を要約して参照し、その書籍固有の観点に集中する
- 他書の `outline.md` と `status.md` を確認して、説明の重複や役割衝突を避ける

## 共通説明ドラフト

### 境界で入力を扱う基本原則

複数の実務書で繰り返し現れるのが、「外部入力はそのまま信用しない」という原則です。API レスポンス、フォーム入力、環境変数、設定ファイル、CLI 引数は、見た目には構造化されていても、受け取る側から見ると未検証の入力です。

基本の流れは次の 3 段階です。

1. 生の入力を受け取る
2. 検証と変換を行う
3. 内部で使う安定した型や構造へ落とす

この原則は TypeScript、Python、Node.js、CLI、設定管理など、複数の書籍で共通して使えます。各書籍ではこの一般論を繰り返すのではなく、それぞれの言語やツールでどこへ実装責務を置くかに集中します。

### 仮想環境と依存関係管理の基本

複数の書籍で重なりやすいのが、「依存関係をどこで固定し、どこまで再現可能にするか」という説明です。Python の仮想環境、Node.js の lockfile、CLI ツールの実行環境は見た目は違っても、目的はかなり近くなります。

基本は次の 4 点です。

1. プロジェクトごとに実行環境を分離する
2. 依存関係の宣言とロックの役割を分けて考える
3. ローカルと CI で同じ手順を使えるようにする
4. 更新はまとめて行わず、影響範囲を見ながら小さく進める

各書籍では、これを一般論として繰り返すよりも、Python の `pyproject.toml` や TypeScript の package 管理のように、各エコシステム固有の判断へ接続する。
