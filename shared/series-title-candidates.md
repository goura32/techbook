# Series Title Candidates

KDP 向けの技術書シリーズとして、共通タイトル部の候補を管理します。
ここでの「共通タイトル部」は、各巻の頭につくシリーズ名を指し、内容説明はサブタイトルで補います。

## 決定事項

- 採用シリーズ名: `技術の輪郭`
- 採用理由:
  - 言語系、OSS 系、規格系、ファイル形式系まで無理なく広げられる
  - 実務寄りにも仕様寄りにも伸ばせる
  - 既存技術書で多い定番表現から少しずらせるため、差別化しやすい

## 方針

- 一般名詞すぎる「入門」「実践」「教科書」単体はシリーズ名にしない
- 他社の既存技術書で多い「現場の」「プログラミング」「みんなの」などの定番パターンは避ける
- 言語系、OSS 系、規格系が同じ棚に並んでも違和感がない抽象度にする
- 技術好きに刺さりつつ、KDP で検索されたときに埋もれにくい固有感を優先する

## 有力候補

### 1. 実装の骨格

- ねらい: 表層の使い方ではなく、実務で崩れない設計と理解を扱う印象を出せる
- 強み: Python、Rust、TypeScript、Git、Docker、USB まで広く載せやすい
- 懸念: 少し硬派で、やや技術者寄り
- 例:
  - 実装の骨格 Python
  - 実装の骨格 Rust
  - 実装の骨格 Git & GitHub
  - 実装の骨格 USB

### 2. 技術の輪郭

- ねらい: 技術の全体像と境界をつかませるシリーズという印象を作れる
- 強み: 言語、OSS、規格、ファイル形式のような題材と相性がよい
- 懸念: 実装寄りの濃さがやや伝わりにくい
- 例:
  - 技術の輪郭 TypeScript
  - 技術の輪郭 Docker/Compose
  - 技術の輪郭 フォントファイル

### 3. 仕様と実装

- ねらい: 「概念だけでも手順だけでもない」ことがひと目で伝わる
- 強み: USB、VRM、フォント、AI エージェント比較のような題材に強い
- 懸念: Git や OBS のような運用寄りテーマだと少し堅い
- 例:
  - 仕様と実装 USB
  - 仕様と実装 VRM
  - 仕様と実装 TypeScript

### 4. 開発の型

- ねらい: 再現性のある実務知識を渡すシリーズとして打ち出せる
- 強み: 言語系、Docker、GitHub、n8n と相性がよい
- 懸念: 規格書系の題材にはやや狭い
- 例:
  - 開発の型 Python
  - 開発の型 Rust
  - 開発の型 Docker/Compose

### 5. 技術をほどく

- ねらい: 難しい技術を分解して理解する、という柔らかい個性を出せる
- 強み: 読み物として親しみやすい
- 懸念: 実務で必要な情報を漏れなく扱う硬派さは少し弱まる
- 例:
  - 技術をほどく USB
  - 技術をほどく フォントファイル
  - 技術をほどく ComfyUI

### 6. 実務の芯

- ねらい: 現場で本当に必要な部分を押さえるシリーズだと伝えやすい
- 強み: 実務志向が明確
- 懸念: 規格系や趣味寄りテーマでは少しトーンが強い
- 例:
  - 実務の芯 Python
  - 実務の芯 Git & GitHub
  - 実務の芯 Docker/Compose

### 7. 技術の足場

- ねらい: 応用や実戦へ進むための基盤を築くシリーズと見せられる
- 強み: 学習シリーズとして展開しやすい
- 懸念: 「最前線」より「基礎固め」に見える
- 例:
  - 技術の足場 Rust
  - 技術の足場 USB
  - 技術の足場 Raspberry Pi

### 8. 実装航路

- ねらい: 仕様や概念から、実際に使える形へ導く印象を持たせる
- 強み: 少し珍しく、シリーズ名として記憶に残りやすい
- 懸念: 好みが分かれる
- 例:
  - 実装航路 TypeScript
  - 実装航路 Docker/Compose
  - 実装航路 n8n

### 9. 技術の地平

- ねらい: 個別技術だけでなく、その周辺や広がりまで見せる印象を出せる
- 強み: 言語、OSS、規格、周辺ツールまで無理なく広げやすい
- 懸念: 実務感はやや弱い
- 例:
  - 技術の地平 Python
  - 技術の地平 USB
  - 技術の地平 Raspberry Pi

### 10. 実装の輪郭

- ねらい: 「技術の輪郭」よりも実装寄りで、理解と実務の両方を示せる
- 強み: 好みとして挙がった2案の中間に置ける
- 懸念: 既存候補同士でやや近い
- 例:
  - 実装の輪郭 Rust
  - 実装の輪郭 Git & GitHub
  - 実装の輪郭 フォントファイル

### 11. 技術の骨格

- ねらい: 「実装の骨格」より一段広く、規格や概念も含めて扱える
- 強み: USB や VRM、フォントのような題材とも相性がよい
- 懸念: 少し抽象的で硬い
- 例:
  - 技術の骨格 TypeScript
  - 技術の骨格 Docker/Compose
  - 技術の骨格 USB

### 12. 開発の輪郭

- ねらい: 技術そのものと、それを使う開発実務の境界を見せる
- 強み: Git/GitHub、Docker、AI エージェント系と相性がよい
- 懸念: USB やフォントファイルではやや狭い
- 例:
  - 開発の輪郭 Python

  - 開発の輪郭 Docker/Compose

### 13. 技術の構図

- ねらい: 部品ごとの説明ではなく、全体の関係性まで整理するシリーズだと見せられる
- 強み: 図解や比較を多く入れるシリーズと相性がよい
- 懸念: 少し評論っぽく見えることがある
- 例:
  - 技術の構図 Rust
  - 技術の構図 Git & GitHub
  - 技術の構図 USB

### 14. 実装の足場

- ねらい: 「技術の足場」よりもコードや手を動かす印象を強める
- 強み: 言語系、Docker、n8n で使いやすい
- 懸念: 規格系にはやや弱い
- 例:
  - 実装の足場 Python
  - 実装の足場 TypeScript
  - 実装の足場 ComfyUI

### 15. 技術の基線

- ねらい: 基礎より一歩先の、判断の基準になる知識を渡す印象を出せる
- 強み: 他シリーズとかぶりにくく、少し知的
- 懸念: 直感的に意味が伝わるまで少し時間がかかる
- 例:
  - 技術の基線 Rust
  - 技術の基線 USB
  - 技術の基線 VRM

### 16. 実務の輪郭

- ねらい: 実務でどこまで押さえればよいかを見せるシリーズとして打ち出せる

- 例:
  - 実務の輪郭 Python

## 第一印象の整理

- `技術の輪郭` は USB、フォントファイル、VRM のように「技術そのものを理解する」本と特に相性がよい
- `実装の輪郭` は Python、Rust、TypeScript、Git & GitHub、Docker/Compose のように「実務でどう作るか」を扱う本と特に相性がよい
- シリーズ全体を一つに寄せるなら `技術の輪郭` のほうが広く展開しやすい
- 言語系と OSS 系を主軸に売るなら `実装の輪郭` のほうが強く見える

## 売り方の観点での比較

### 技術の輪郭

- 強い点:
  - 規格系、ファイル形式系、言語系、OSS 系をひとつの棚に並べやすい

  - 長期的にテーマを増やしても破綻しにくい
- 弱い点:
  - 実務色はサブタイトル側で補わないと弱く見える
  - Kindle ストア上では、やや抽象的に見える可能性がある
- 向いている題材:
  - USB
  - フォントファイル
  - VRM
  - TypeScript
  - Docker/Compose

### 実装の輪郭

- 強い点:
  - 実務書としての圧が出る

  - サブタイトルが多少平易でも、内容の濃さが想像しやすい
- 弱い点:
  - USB やフォントファイルのような「理解中心」の題材では少し狭く感じる場合がある
  - 将来的に規格系を増やしたとき、やや実装寄りに寄りすぎる可能性がある
- 向いている題材:
  - Python
  - Rust
  - TypeScript
  - Git & GitHub
  - Docker/Compose
  - n8n

## サブタイトルの型

シリーズ名が抽象寄りなので、サブタイトルは毎回次のどれかに寄せる。

### 型 A

- `主要テーマ + 実務で扱う範囲`
- 例: 型システム、設計、ビルド、運用を横断して理解する

### 型 B

- `読者が得る状態 + 主要トピック`
- 例: 壊れにくく保守しやすいコードのための実務設計

### 型 C

- `基礎概念 + 応用領域 + 現場テーマ`
- 例: 規格、転送、電力、列挙、解析を実装視点で学ぶ

## 現時点の暫定結論

- シリーズ全体の広がりを優先するなら `技術の輪郭`
- 最初の数冊の売れ筋を優先するなら `実装の輪郭`
- いま挙がっている候補群全体を見る限り、長期的には `技術の輪郭` がわずかに有利
