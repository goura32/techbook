# 7章 Profiles、SOUL.md、Context Files の設計

Hermes Agent を継続運用したいなら、Profiles、`SOUL.md`、Context Files の役割を早めに整理しておく必要があります。ここが曖昧だと、会話履歴、Skill、memory、個別の指示が全部同じ場所で競合し始めます。結果として「たまにうまくいくが、なぜうまくいったか説明しにくい」状態になります。

Profiles は、人格を分けるためのものではありません。責務、権限、作業範囲、前提を分けるためのものです。`ForgeFlow` で `coder` `triage` `ops` を分けるのも、キャラクター性のためではなく、触る対象と判断の責任を分けるためです。ここを誤解すると、profile が増えるほど運用は楽になるどころか複雑になります。

`SOUL.md` に書くべきなのは、長く維持したい原則です。何を優先するか、どこで人間へ確認を戻すか、どのような変更を避けるか。反対に、毎回変わる作業指示や、特定案件だけの細かな情報はここへ書かないほうがよいです。`SOUL.md` を万能なメモ帳にすると、profile ごとの差が見えなくなります。

Context Files は、より局所的な前提を固定するのに向いています。特定プロジェクトの構成、リポジトリ固有の注意点、チームのレビュー観点、ログの読み方。こうした情報は毎回会話で説明するには長く、memory に丸投げするには変化しやすい領域です。Context Files は、その中間を埋める役割を持ちます。

重要なのは、共有してよい前提と、分けるべき前提を意識することです。たとえば「このリポジトリでは変更前にテストを確認する」は共通原則かもしれませんが、「Issue の優先度付けルール」は `triage` の前提として閉じたほうがよいかもしれません。全部共有すると profile の意味が薄れ、全部分けると保守が重くなります。ちょうどよい線を探る必要があります。

profile が増えすぎる失敗にも注意が必要です。責務を切ろうとして、実際には似た profile が複数生まれ、どれを使うべきか人間側が迷うようになることがあります。そのとき見直すべきなのは「profile が足りないか」ではなく、「Skill や Context Files で吸収できる揺れを、profile へ押し込んでいないか」です。

付録 A と付録 B は、この章で特に役に立ちます。`ForgeFlow` 全体の構成を見返したいときは付録 A、profile と capability の対応を確認したいときは付録 B が向いています。次の章では、こうして分けた profile が長い時間軸の中で何を覚えるべきか、何を覚えさせないべきかを、Memory と external providers の観点から見ていきます。
