# 9章 Checkpoints と安全な変更

Hermes Agent がファイルを触るようになると、便利さと同時に不安も増えます。どこまで書き換わったか、意図しない変更が混ざっていないか、壊したときにどう戻すか。ここで効いてくるのが Checkpoints です。ただし、Checkpoints は「安心ボタン」ではありません。変更を可逆にするための変更管理機能として捉えたほうが、実務ではずっと役に立ちます。

まず大事なのは、どんな仕事の前に checkpoint を切るべきかを決めることです。大きなファイル変更、複数ファイルをまたぐ修正、設定の更新、外部接続を含む長いタスク。こうした仕事では、成功したときの利便性より、失敗したときの戻しやすさが重要です。反対に、読み取りだけの仕事では checkpoint を毎回切る必要はありません。

`ForgeFlow` では、`coder` profile が実際にファイルを修正する前、`ops` が運用設定を変更する前には checkpoint を前提にします。ここでのポイントは、checkpoint を切ること自体より、「どこからどこまでをひとつの変更単位とみなすか」を人間が先に意識することです。checkpoint の粒度が粗すぎると戻しにくく、細かすぎると運用が重くなります。

rollback も、自動で全部解決してくれるわけではありません。戻したあとに何を確認するか、関連する外部状態をどう扱うか、途中まで成功した副作用がないか。つまり checkpoint は「戻る場所」を作る仕組みであって、「戻ったあとに安全であること」を保証する仕組みではありません。そこは人間の復旧手順が必要です。

このため、Checkpoints は Git と競合するものではなく、補完するものとして見ると分かりやすくなります。Git が長い時間軸の変更管理を担うなら、Checkpoints はエージェント作業中の短い時間軸の保険です。エージェントが途中でおかしな方向へ進んだとき、全部を人手で巻き戻す前に、一段前へ戻せる価値は大きいです。

ただし、checkpoint がある前提で雑になる危険もあります。どうせ戻せるからといって広い権限を雑に与えたり、確認を飛ばしたりすると、戻せる回数だけ事故を繰り返すことになります。checkpoint は無秩序を許す機能ではなく、秩序ある変更を支える機能です。付録 C の設定断片でも、この章の考え方に沿って checkpoint を前提にした例を置いています。

Checkpoints と rollback の感覚が掴めると、CLI 利用から一段進んだ長時間運用の土台ができます。次の章では、その先にある Gateway と Cron を扱い、常駐運用を始める前に何を決めるべきかを整理します。
