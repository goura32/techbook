# 12章 OpenCode / OpenClaw と比較した採用判断

Hermes Agent を評価するとき、避けて通れないのが他の OSS エージェントとの比較です。特に OpenCode と OpenClaw は話題性も高く、使いどころも近く見えます。ただし、この比較で大切なのは機能の数を並べることではありません。実務で本当に必要なのは、「自分の運用要件に対して、どの構造が一番説明しやすいか」を判断することです。比較の入口としては表12-1も参照してください。

## 表12-1 Hermes / OpenCode / OpenClaw の比較

| ツール | 強み | 注意点 |
| --- | --- | --- |
| Hermes Agent | 設定、Profiles、Memory、Cron をまとめて設計しやすい | 更新が速く構成も広い |
| OpenCode | coding workflow 中心の体験に強い | 長時間運用や責務分離は別途見極めが必要 |
| OpenClaw | プラットフォームの広さ | 対象範囲が広く、導入設計が重くなりやすい |

この表は優劣表というより、採用判断の入口です。自分の現場が何を求めているかに戻るために使います。

## 12-1. 比較の軸を先に決める

比較で最初に決めるべきなのは、何を重視するかです。本書では次の軸を勧めます。

- 入口
  - CLI 中心か
  - UI 中心か
- 状態管理
  - profile や memory をどこまで構造化できるか
- 外部能力
  - MCP や外部連携をどう扱うか
- 長時間運用
  - cron、messaging、observability をどこまで持つか
- 安全性
  - approvals、rollback、secrets、logs をどう扱うか

この軸がないと、比較はすぐ「人気があるか」「機能が多いか」という雑な話になります。

## 12-2. CLI 中心利用での違い

CLI を中心に、手元のワークフローを少しずつ構造化したいなら、Hermes Agent はかなり相性がよいです。設定ファイル、profile、Skill、MCP、Cron までが比較的ひとつの系として見えやすいからです。

一方で、他ツールのほうが次の点で強いこともあります。

- UI や体験の即効性
- 特定用途への最適化
- より軽い導入感

つまり、Hermes Agent は「最速で体験できる」ことより、「増やした構成を説明しやすい」ことに強みがあります。

## 12-3. Profiles、Memory、Gateway、Cron で見る違い

本書で Hermes Agent を高く評価しているのは、単にコードが書けるからではありません。Profiles、Context Files、Memory Providers、Checkpoints、Gateway、Cron という層があるので、責務分離と長時間運用の設計をひとつの枠で考えやすいからです。

この特徴が効くのは次のような現場です。

- 個人利用からチーム運用へ広げたい
- 役割ごとに state を分けたい
- 一部の仕事だけを常駐化したい
- secrets や approvals を早い段階から意識したい

## 12-4. Hermes Agent が向く現場、向かない現場

向く現場:

- 手順を資産化したい
- profile ごとに責務を分けたい
- Gateway や Cron を段階的に足したい
- 設定ファイルと CLI の両方を整理したい
- 長く保守する前提で設計したい

向かない現場:

- すぐに体験できる軽さを最優先する
- 長時間運用や複数チャネル連携は不要
- profile や memory の層を考えるコストを負いたくない
- 構造化より、その場の対話速度を優先したい

## 12-5. 2026年5月14日時点での採用判断の残し方

この分野は更新が速く、機能差は短期間で変わりえます。だから本書では、バージョンごとの差分一覧より、採用判断の軸を残すことを重視しました。

- どの入口を主戦場にするか
- どこまで state を持たせるか
- どこで人間が止めるか
- 常駐運用をどこまで求めるか
- 更新時に何を点検するか

## 12-6. この章のまとめ

比較の結論は「Hermes Agent が常に最良」ではありません。自分の運用要件に対して、どの構造が一番説明しやすいかを選べるようになることこそ、この章の着地点です。
