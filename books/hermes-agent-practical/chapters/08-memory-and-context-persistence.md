# 8章 Memory、Memory Providers、文脈の持続

AI エージェントを継続利用すると、必ず「覚えていてほしい」という欲求が生まれます。毎回同じ前提を説明したくない、過去の判断を踏まえてほしい、チームの流儀を引き継いでほしい。その気持ちは自然ですし、Hermes Agent でも memory は確かに便利です。ただし、memory は便利さと引き換えに、見えにくい状態を増やします。ここを理解せずに使うと、構成全体が急に説明しにくくなります。

まず分けて考えたいのは、memory は設計不足を埋める魔法ではないということです。profile が曖昧、Context Files が足りない、Skill が揺れている、そうした問題を memory で補おうとすると、あとで何がどこに効いているのか分からなくなります。memory は、明示的な前提を補助するためのものです。

Hermes Agent には built-in memory と external providers という複数の選択肢があります。ここで大事なのは、どちらが高機能かではなく、どこまで状態を持たせる必要があるかです。短い時間軸の補助なら built-in memory で足りるかもしれませんし、セッションやチャネルをまたぐ持続が必要なら external providers が向くかもしれません。必要以上に長く残すと、便利さより曖昧さが増えます。

`ForgeFlow` で覚えさせたいものを考えると、たとえば issue の分類基準やレビュー時の観点は、memory に置くより Skill や Context Files へ固定したほうが扱いやすいです。一方で、継続的に監視している対象の直近状態や、セッションをまたいで引き継ぎたい短い文脈は、memory が役立つ場面です。つまり、原則は静的な文書へ、変化する短期状態は memory へ寄せるほうが安定します。

memory を使うなら、更新と削除の方針も先に決めます。誤ったことを覚えたとき、古い前提が残ったとき、不要になったときに、誰がどう直すのかが見えていないと危険です。人間のメモと違って、agent の memory は「どこで効いているか」が見えにくいことがあります。だから、覚えることだけでなく、忘れさせることも運用設計の一部です。

Memory Providers を足すと、外部接続、認証、可用性、監査という新しい論点も増えます。つまり memory は、内部便利機能というより、外部状態を持つシステムに近づく一歩です。ここまで来たら、便利さだけでなく、障害時にどう切り離すか、誤学習時にどう戻すか、人間が確認できる形で何を残すかをセットで考える必要があります。

この章の結論は単純です。memory は強いが、強いからこそ使いすぎないほうがよい、ということです。次の章では、状態を持つ運用のもうひとつの安全装置として、Checkpoints と rollback をどう位置づけるかを見ていきます。
