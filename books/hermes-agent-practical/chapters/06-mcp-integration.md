# 6章 MCP 連携で広げる能力

Hermes Agent の魅力のひとつは、MCP を通じて外部の能力を足せることです。リポジトリ、課題管理、ドキュメント、ブラウザ、自作ツール。こうしたものへ agent が触れられるようになると、たしかに世界は広がります。ただし、MCP は「できることが増える機能」であると同時に、「責任範囲が広がる機能」でもあります。ここを同時に見ないと、構成はすぐ不安定になります。

最初に考えるべきなのは、「その能力を本当に agent 側へ渡す必要があるか」です。たとえばローカルファイルの読み書きだけで十分なら、わざわざ外部接続を増やす意味は薄いかもしれません。反対に、Issue の状態確認や外部ドキュメント参照のように、手作業で毎回渡すには負担が大きい情報は、MCP の恩恵を受けやすい領域です。

`ForgeFlow` では、`triage` に課題管理系の MCP、`coder` に必要最小限の開発支援系 MCP を足す構成が自然です。このとき重要なのは、「profile ごとに必要な接続だけを持つ」ことです。全部の profile が全部の MCP を使える構成は、設定が楽に見えても、監査と切り戻しが難しくなります。能力は共有財ではなく、責務に応じて分割したほうがよいのです。

認証と接続先の扱いも、MCP ではとても重要です。どの資格情報を誰が管理するか、失効時にどう気づくか、接続先の障害をどう検知するか。モデルの賢さだけでは吸収できない運用論がここにはあります。MCP を足した瞬間に、Hermes Agent はローカルの CLI ツールから、外部状態に依存するシステムへ少し近づきます。

失敗時の扱いも先に考えておきたいところです。MCP が失敗したとき、再試行してよいのか、中断すべきか、人間へ確認を戻すべきか。ここを曖昧にすると、agent は一見動いているのに結果が信用しにくい状態になります。だから本書では、MCP の導入を「便利な拡張」より、「障害点を増やす設計変更」としても見ます。

MCP が増えると、構成情報そのものも負債になります。どの profile がどのサーバーへ接続し、どの Skill がそれを前提にしているかが見えなくなるからです。付録 C には `ForgeFlow` の設定断片を置いていますが、そこで注目したいのは書式ではなく、どの能力がどの profile に閉じているかです。接続が増えても、責務は散らさないことが大切です。

MCP は強力ですが、導入順を誤ると最も不安定さを増やしやすい場所でもあります。だからこそ次の章では、能力を広げる前に前提を固定するための Profiles、`SOUL.md`、Context Files の設計を整理します。外へ触れる能力が増えるほど、内側の前提は明示的である必要があります。
