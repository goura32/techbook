# 3章 モデル、プロバイダ、ツール権限の考え方

Hermes Agent を使い始めると、ついモデル選びに意識が寄りがちです。どのモデルが賢いか、どの provider が安いか、どの組み合わせが速いか。もちろんそれも大事ですが、実務ではそれ以上に「そのモデルへ何を渡し、何を触らせるか」の設計が効きます。同じモデルでも、権限と環境の切り方で安全性も再現性も大きく変わるからです。

まず分けて考えたいのは、モデルと provider は能力の供給源であり、ツール権限は責務の境界だということです。モデルを強くしても、曖昧な権限設計は改善しません。逆に、権限を小さく切り、作業範囲を明確にしておけば、多少モデルが揺れても大事故にはつながりにくくなります。Hermes Agent の運用では、賢さより境界の明示が先です。

provider 設定は、モデルの種類だけでなく、認証方法、接続先、課金単位、障害時の切り替えやすさまで含めて見ます。ひとつの provider に深く依存してもかまいませんが、そのときも「差し替えられる前提」で設定を持つほうが長く効きます。`ForgeFlow` でも、`coder` と `ops` が同じ provider を使うとしても、責務は設定側で分けておきます。

ツール権限で特に重要なのは、端末実行とファイル書き込みです。これらは便利さに直結する一方、事故の影響も大きいからです。たとえば `triage` profile には読み取りと issue 整理だけを担わせたいのに、広いターミナル権限と書き込み権限を与える必要はありません。`coder` には限定された作業ディレクトリを渡し、`ops` には監視系の操作だけを残す、といった分離が効きます。

このとき大事なのは、profile は sandbox ではないという理解です。profile を分けたから安全になるのではなく、profile ごとに責務、利用する tool、作業ディレクトリ、前提文書を変えることで安全性を高めます。つまり profile は人格分離ではなく、運用の切り口です。この理解が曖昧だと、profile を増やしても実態は何も変わりません。

観測点もここで一緒に設計したいところです。どのツールを使ったか、どのファイルを触ったか、どの profile が動いたかが分からない運用は、事故時にとても弱くなります。権限を広げるなら、それに比例してログや確認手順も増やすべきです。便利さだけを先に増やすと、「失敗したときに人間が説明できない」状態が起きます。

付録 C には、`ForgeFlow` で使う profile と設定断片の例を載せています。ここで見たいのは書式そのものではなく、なぜ `coder` にその権限だけを渡すのか、なぜ `ops` の作業範囲を狭めるのかです。次の章では、その前提を踏まえて、CLI 中心の日常利用をどう整えると無理なく続くかを見ていきます。
