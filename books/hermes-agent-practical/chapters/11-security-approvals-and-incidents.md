# 11章 セキュリティ、承認、事故対応

Hermes Agent のようなツールを実務へ入れるとき、最後まで軽く見てはいけないのがセキュリティです。AI エージェントの話題では、つい能力や速度が前に出ますが、運用上の本当の差は「事故が起きたとき、どれだけ小さく閉じられるか」に出ます。その意味で、secrets、approval、redaction、logs、停止手順は、便利機能より先に固めたい要素です。最低限の確認項目は表11-1も参照してください。

## 表11-1 セキュリティと承認のチェックリスト

| 観点 | 確認項目 |
| --- | --- |
| secrets | `.env` や secret store に分離されているか |
| approval | 外部投稿と広い変更に境界があるか |
| logs | 残す情報と隠す情報が決まっているか |
| rollback | 変更前へ戻る導線があるか |
| long running | job を止める手順があるか |

導入前や更新後にこの表へ戻るだけでも、見落としをかなり減らせます。

## 11-1. secrets をどこへ置くか

最初の原則は単純です。秘密情報は `.env` または適切な外部 secret 管理へ置き、`config.yaml` や文書へ混ぜないことです。API key、bot token、外部サービス認証、observability の secret は、まず置き場所を固定します。

ここでやりがちな失敗は次です。

- 試しに入れた token を `config.yaml` に残す
- Context Files や `SOUL.md` に接続情報を書いてしまう
- debug のために生の credential をログへ出す

## 11-2. approval は責任の境界

approval は速度を落とす仕組みではありません。どこまでを agent に任せ、どこからを人間の責任に戻すかを明示するための仕組みです。

- 読み取り: 自動
- ファイル変更: approval
- 外部投稿: 別 approval
- 広い shell 実行: 強い approval

全部を止めるのではなく、「ここを越えるなら人間が見る」という境界を作ることが重要です。

## 11-3. redaction と logs の役割

長時間運用や外部連携を始めると、logs の価値は一気に上がります。ところが、ログを増やすほど secrets 流出リスクも増えます。そこで redaction が必要になります。

見るべき観点は次です。

- 何を記録するか
- 何をマスクするか
- 誰がそのログを見るか
- 障害切り分けに必要な粒度はどこまでか

全部を残せば安全になるわけではありません。残しすぎると危険が増え、残さなすぎると事故時に何も追えません。

## 11-4. 典型的な事故パターン

Hermes Agent の運用事故は、おおむね次の型に分けて見ると整理しやすいです。

1. ファイル変更事故
2. 外部投稿事故
3. 長時間運用事故
4. 文脈事故
5. 認証事故

この分類の価値は、原因を細かく言い当てることではなく、最初の止め方を決めやすくすることです。

## 11-5. 最低限の事故初動

実務では、事故が起きた瞬間に完璧な原因究明はできません。だからこそ、最初の10分でやることを固定しておく価値があります。

1. 影響する profile と job を止める
2. 直近の通知先と対象ファイルを確認する
3. credential の失効が必要か判断する
4. rollback か設定差し戻しを実施する
5. 再開条件が決まるまで常駐運用を広げない

## 11-6. 導入時と更新時の監査ポイント

Hermes Agent のように更新が速いツールでは、導入時だけでなく更新時の点検も重要です。

- 新しい config 項目が増えていないか
- env var の扱いが変わっていないか
- approval や redaction に関係する挙動が変わっていないか
- gateway / cron の既定値が変わっていないか

2026年5月14日時点の公式 docs でも `hermes config check` や `migrate` の導線があるのは、この更新点検が必要だからです。

## 11-7. この章のまとめ

セキュリティは便利機能の脇役ではなく、運用設計の中心です。どこへ secret を置くか、どこで approval を入れるか、事故時に何から止めるかを先に決めておくと、Hermes Agent の柔軟さをかなり安全に扱えるようになります。承認、security、logging、updates の完全表は付録F、secret や process-level override の補助情報は付録Hを参照してください。
