# 11章 セキュリティ、承認、運用事故への備え

Hermes Agent のようなツールを実務へ入れるとき、最後まで軽く見てはいけないのがセキュリティです。AI エージェントの話題では、つい能力や速度が前に出ますが、運用上の本当の差は「事故が起きたとき、どれだけ小さく閉じられるか」に出ます。その意味で、承認、redaction、credential の扱い、停止手順は、便利機能より先に固めたい要素です。

最初の原則は、便利さと権限を同時に上げないことです。MCP を足した、memory を持たせた、Cron で回し始めた、そのうえで広いファイル権限や外部チャネル書き込み権限も一緒に開けると、どの拡張がどのリスクを増やしたのか追えなくなります。構成を一段ずつ広げ、そのたびに確認点を増やすほうが安全です。

承認設定は、Hermes Agent を信用していないから入れるのではありません。人間と agent の責任境界を明示するために入れます。たとえば読み取りだけは自動、ファイル変更は承認、外部投稿は別承認といった線引きがあると、使う側も安心して任せられます。承認は速度を下げる仕組みではなく、任せられる範囲を広げる前提です。

資格情報の扱いも重要です。API キー、トークン、接続先設定は、agent から見て便利な入力ですが、人間から見れば漏らしてはいけない資産です。redaction や credential 管理の仕組みは、便利さの補助ではなく必須の防御層として扱うべきです。特に外部チャネルや debug 共有のような経路では、どこまで情報が出るかを明確にしておく必要があります。

事故の種類も、あらかじめ想像しておいたほうがよいです。想定外のファイル変更、誤った issue 更新、外部投稿の誤配信、memory への不適切な記憶、MCP 接続の誤動作。これらはすべて別の事故ですが、共通するのは「すぐ止められること」と「どこまで影響したかを追えること」が大切だという点です。だからログ、checkpoint、承認、profile 分離は別々の話ではなく、事故対応のための部品でもあります。

`ForgeFlow` でも、`coder` に広い投稿権限は持たせず、`ops` に広い書き込み権限は与えません。これは能力を削っているのではなく、事故時の切り分けを簡単にしているのです。何が壊れたかより、どこまで壊しうるかが分かっている運用のほうが、はるかに扱いやすくなります。

付録 C の断片は、この章で特に見返しやすいはずです。設定例そのものより、「何を止め、何を残し、何を分けるか」を確認するのに使ってください。最後の章では、ここまで整理した観点を持って、OpenCode と OpenClaw を比較対象として見たとき、なぜ Hermes Agent を選ぶのか、あるいは選ばないのかを整理します。
