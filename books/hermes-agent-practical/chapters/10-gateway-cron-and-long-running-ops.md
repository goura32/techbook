# 10章 Gateway、Cron、長時間運用

CLI で Hermes Agent が役立ち始めると、次に気になるのが常駐運用です。チャット経由で使いたい、定期的に見回らせたい、障害の兆候を監視させたい。Gateway や Cron は、その欲求に応えるための仕組みです。ただし、この段階に入ると、Hermes Agent は個人の作業補助から、半ば運用システムの一部へ変わります。ここで必要になるのは、便利さより運用設計です。

CLI と常駐運用の決定的な違いは、誰が開始し、誰が停止し、誰が状態を把握するかです。CLI なら、手元で呼び出した人がほぼ全責任を持てます。Gateway や Cron では、実行のきっかけと、結果を受け取る人と、問題に気づく人が分かれやすくなります。だから、単に「同じ依頼を自動化する」だけでは足りません。

Gateway を入れるなら、まず考えるべきなのは接続先の広がりと観測点です。どのチャネルから受け付けるのか、誰が使えるのか、どの profile が動くのか、途中状態をどこで確認するのか。これらが曖昧なまま運用を始めると、動いているのに誰も全体像を説明できない状態になります。

Cron も同様です。Hermes Agent を使って定期実行させるのか、`no_agent` のような script-only 的な監視に留めるのかで、必要な安全装置が変わります。単純な生存確認や固定ルールの検査なら、agent を介さないほうが安定することもあります。毎回 agent を使うことが高度なのではなく、何を agent に任せる価値があるかを見極めることが重要です。

`ForgeFlow` では、`ops` profile による定期監視を考えますが、その役割は「自動で何でも処理する」ことではありません。未対応 Issue の棚卸し、監視対象の変化検出、一定条件での通知のように、人間が次の判断をしやすくする仕事へ絞ります。長時間運用で一番危ないのは、判断を完全自動化したつもりになって観測をやめることです。

そのため、運用を始める前に停止条件を決めておく必要があります。どの失敗で止めるのか、何回失敗したら人間へ戻すのか、接続障害時はどう扱うのか。便利な自動化は、やめ方が決まっていて初めて安全になります。ここは通常のソフトウェア運用と同じです。

2026年5月13日時点の Hermes Agent では、Gateway や Cron まわりの機能もかなり広がっていますが、だからこそ全部を一度に使わないことが大切です。CLI で安定した profile と Skill、MCP、Checkpoint の設計ができてから長時間運用へ進むほうが、結果的に速く安全です。次の章では、その長時間運用を現実的に支えるためのセキュリティ、承認、事故対応を整理します。
