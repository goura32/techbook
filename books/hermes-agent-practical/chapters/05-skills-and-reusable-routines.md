# 5章 Skills と再利用可能な手順設計

Hermes Agent をしばらく使うと、うまくいく依頼には共通の型があることに気づきます。差分レビューの観点、テスト失敗の読み方、Issue の分類基準、変更提案の出し方。これらを毎回手で説明していると、少しずつ言い回しがぶれ、期待値も揺れます。そこで効いてくるのが Skills です。

Skills は、単なる長いプロンプトではありません。再利用したい手順、前提、観点を資産として分離する仕組みです。プロンプトのコピペとの違いは、どこで使うか、誰が更新するか、どの profile と組み合わせるかを意識できることにあります。つまり Skill は、Hermes Agent の振る舞いを安定させる手順書です。

Skill に切り出す価値が高いのは、仕事の目的が毎回同じで、見るべき観点もだいたい決まっているものです。たとえば `ForgeFlow` では、`triage` が issue を読んで優先度や担当候補を整理する仕事、`coder` が差分の保守性観点だけを点検する仕事などは Skill 化しやすい領域です。逆に、探索的な議論や要件未確定の設計検討は、最初から Skill にしないほうがよいことも多いです。

ここで気をつけたいのは、Skill は権限ではないということです。Skill に「このリポジトリを全部修正してよい」と書いても、安全にはなりません。安全性は profile と tool 権限、作業ディレクトリ、承認設定で作られます。Skill が担うのは、どの順で見て、何を重視し、何を出力すべきかという作業手順です。

Skill の粒度も重要です。細かすぎる Skill は組み合わせが複雑になり、粗すぎる Skill は再利用性が落ちます。よい粒度の目安は、「この仕事なら毎回この観点を使う」と言えるかどうかです。レビュー観点、Issue 分類、障害初動の切り分けなどは比較的切り出しやすく、反対に「なんとなく賢くやってほしい」は Skill 化しにくい仕事です。

更新ルールも先に決めておくと、あとで楽になります。誰が直せるのか、いつ見直すのか、失敗が起きたとき Skill を疑うのか profile を疑うのか。こうした手順がないと、Skill はいつの間にか肥大化し、説明責任のないブラックボックスになりやすいです。付録 B では、`ForgeFlow` でどの profile がどの Skill を使うかの対応を見返せるようにしています。

Skill は、日常 CLI 利用から得た成功パターンを固定するための仕組みです。次の章で扱う MCP は、それとは別に、Hermes Agent が外部能力へ触れるための仕組みです。つまり Skill は「どう考えるか」を、MCP は「何へ触れるか」を分担します。この切り分けを押さえておくと、構成がかなり整理しやすくなります。
