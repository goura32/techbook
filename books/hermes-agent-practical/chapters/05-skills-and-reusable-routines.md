# 5章 Skills と再利用可能な作業手順

Hermes Agent をしばらく使うと、うまくいく依頼には共通の型があることに気づきます。差分レビューの観点、Issue の分類基準、テスト失敗時の見方、依存更新の確認順序。これらを毎回の会話で手打ちしていると、少しずつ言い回しがぶれ、成功条件も曖昧になります。そこで効いてくるのが Skills です。Skill に向く仕事の特徴は表5-1も参照してください。

## 表5-1 Skill に切り出すべき手順の特徴

| 向いている手順 | 理由 |
| --- | --- |
| 同じ観点で繰り返す review | 出力のぶれを減らせる |
| 調査手順が固定される仕事 | 会話履歴依存を減らせる |
| 複数ツールをまたぐ定型作業 | 手順を資産化できる |

この表のどれにも当てはまらない仕事は、無理に Skill 化しないほうがうまくいくことが多いです。

## 5-1. Skill は長いプロンプトではない

Skill は、単なる長いプロンプトではありません。再利用したい手順、前提、確認観点、出力形式を、日常の会話から切り出して固定するための仕組みです。違いは「長いか短いか」ではなく、`再利用前提で保守するかどうか` にあります。

会話へ貼り付けた手順は、その場では役立ちますが、後から更新しにくく、誰がどこを直したのかも見えません。Skill にすると、少なくとも次の問いへ答えやすくなります。

- 何のための手順か
- どの profile と組み合わせるか
- どの出力を期待するか
- 失敗したらどこを見直すか

## 5-2. Skill に向く仕事、向かない仕事

Skill に向くのは、目的と観点が比較的固定されている仕事です。`ForgeFlow` でいえば、次のようなものです。

- `triage`
  - issue を要約して優先度候補を出す
- `coder`
  - 差分の保守性だけを見る
  - failing test から原因候補を挙げる
- `ops`
  - 依存更新 PR の確認観点を固定する

一方で、次のような仕事は Skill にしすぎないほうがよいことがあります。

- 要件が固まっていない設計議論
- 毎回観点が大きく変わる調査
- その日限りの一時的な運用

Skill は万能化すると弱くなります。毎回違うものまで押し込むと、「結局なんでもやる曖昧な手順」になりがちです。

## 5-3. Skill と profile と権限を混同しない

ここでよく起きる誤解が、Skill を権限だと思ってしまうことです。Skill に「リポジトリ全体を安全に修正する」と書いても、安全にはなりません。安全性は、profile、toolset、approval、作業ディレクトリ、backend で作られます。

Skill が担うのは次のような部分です。

- どの順序で見るか
- 何を重視するか
- 何を出力するか
- どこで人間へ戻すか

つまり Skill は手順書であり、権限ではありません。この線引きが曖昧だと、「Skill を増やしたのに事故が減らない」という状態になります。

## 5-4. 粒度と命名を先に決める

保守しやすい Skill には、共通して次の特徴があります。

- 1 つの目的が明確
- 出力形式が決まっている
- 他の Skill と責務が重なりすぎない
- 失敗したときに修正箇所を特定しやすい

たとえば `review-large-pr` のように何でも詰め込むより、`review-diff-maintainability` や `summarize-failing-tests` のように、観点と出力を絞ったほうが保守しやすくなります。名前は技術ではなく目的で付けるほうが、あとで見直しやすくなります。

## 5-5. Skill をどう更新するか

商用レベルの運用では、Skill の更新ルールも必要です。たとえば次のような決め方が有効です。

- 失敗が2回続いたら Skill を疑う
- profile を増やす前に Skill の粒度を見直す
- 出力形式を変えたらサンプルも更新する
- 依存している tool や MCP が変わったら関連 Skill を点検する

Skill は「一度作って終わり」ではなく、運用資産です。ここを軽く見ると、再利用のつもりで増やした Skill が、かえって説明しにくいブラックボックスになります。

## 5-6. この章のまとめ

Skill は、CLI で見つかった成功パターンを固定するための仕組みです。何でも Skill 化するのではなく、目的と出力が固定しやすい仕事だけを切り出すことが重要です。次の章では、その Skill や profile だけでは足りない能力を、MCP でどのように外へ接続するかを見ます。
