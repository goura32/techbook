# 1章 Hermes Agent とは何か

Hermes Agent を最初に触ったとき、多くの人は「よくできた AI エージェントのひとつ」として見ます。CLI から指示を出せる、ツールを呼べる、ファイルを触れる、長い会話もある程度保てる。その理解は間違いではありません。ただ、実務で長く使うなら、それだけでは足りません。重要なのは、Hermes Agent を単なる対話相手ではなく、設定し、制限し、観測し、更新していく運用対象として捉えることです。

本書で Hermes Agent を扱うときの中心的な視点は、`境界で制限し、内部で再利用する` ことです。AI エージェントは便利さのぶんだけ曖昧さを持ち込みます。どのディレクトリまで触れてよいのか、どのツールを呼んでよいのか、何を記憶し、何を覚えさせないのか。ここが曖昧なまま使い始めると、短期的には速く見えても、長期的には事故や不信感の原因になります。

Hermes Agent が面白いのは、単にモデルへプロンプトを投げるだけでなく、Profile、Skills、MCP、Memory、Checkpoints、Gateway、Cron のような部品を通じて、使い方を構造化できるところです。これは「全部使える」という意味ではありません。むしろ、どれを使わないかを決められることが大切です。単発の補助なら CLI と少数の Skills で十分ですし、継続的な運用が必要なら Profile 分離や Checkpoints が効きます。

その違いを追うため、本書では `ForgeFlow` という小さな通しサンプルを使います。`ForgeFlow` は、Issue の整理、コード変更、レビュー補助、定期監視を Hermes Agent に段階的に任せていく開発支援基盤です。最初から巨大な構成を作るのではなく、`coder` `triage` `ops` の 3 profile を少しずつ育てながら、どこで Skills が効き、どこで MCP が必要になり、どこで Memory や Cron が欲しくなるかを同じ題材で追います。

ここで重要なのは、Hermes Agent は「何でも自律的にやらせる」ための道具ではないということです。よい運用は、任せる範囲が明確で、止める条件があり、失敗時の戻し方が決まっています。たとえばコード生成だけなら `coder` profile に限定した権限で十分ですし、Issue 監視だけなら `ops` profile に広い書き込み権限は不要です。能力を足すことより、責務を分けることが先に来ます。

Hermes Agent を採用する価値は、ここにあります。毎回の指示でゼロから前提を説明するのではなく、ある程度固定された profile、再利用できる Skills、明示的な Context Files を持つことで、同じ仕事を繰り返す負担を減らせます。そのうえで Checkpoints や承認設定を入れれば、便利さと安全性の両方をある程度確保できます。言い換えると、Hermes Agent の強みは単発の賢さより、継続利用時の構造化にあります。

もちろん、注意点もあります。機能が多いぶん、早い段階で複雑にしすぎやすいことです。Skill を細かく分けすぎる、profile を増やしすぎる、memory に何でも覚えさせる、MCP を大量に足す。こうした構成は一見高度に見えますが、運用の見通しを悪くしがちです。だから本書では、便利な機能を全部紹介するのではなく、「どこで止めるか」を含めて書きます。

まずは Hermes Agent の全体像を、「会話相手」から「運用する道具」へ見方を変えるところから始めます。`ForgeFlow` の全体配置を先に見返したいときは付録 A が役に立ちます。次の章では、2026年5月13日時点の公式導入経路を前提に、最初のセットアップをどこまでやるべきかを整理します。
