# 4章 CLI 中心の日常ワークフロー

Hermes Agent の日常利用で最初の主戦場になるのは、やはり CLI です。常駐運用や複数チャネル連携は魅力的ですが、そこへ進む前に「どんな依頼を、どの profile へ、どの引数で渡すと安定するか」を掴む必要があります。CLI は、その感覚を作るための最良の観測地点です。日常で使う主要引数は表4-1も参照してください。

## 表4-1 `hermes chat` の主要引数

| 引数 | 主な用途 |
| --- | --- |
| `--model` | model 上書き |
| `--provider` | provider 上書き |
| `--skills` | skill 指定 |
| `--toolsets` | toolset 指定 |
| `--checkpoints` | checkpoint 前提 |
| `--ignore-user-config` | 切り分け |
| `--ignore-rules` | 切り分け |

ここでは、日常で本当に使うものだけを抜き出しています。全部の CLI を暗記するより、この表のような「よく触る引数」を安定して使えるほうが実務では重要です。

## 4-1. `hermes chat` を土台にする理由

公式の CLI Commands を見ると、Hermes Agent には `chat` を中心に、`config` `model` `auth` `mcp` `tools` `cron` `profile` など多くの入口があります。ここで大事なのは、最初から全部を使い分けることではありません。日常運用の土台としては、まず `hermes chat` と `hermes config` を安定させるだけで十分です。

日常の補助で知っておきたい代表的な引数は次です。

- `--model`
- `--provider`
- `--skills`
- `--toolsets`
- `--worktree`
- `--checkpoints`
- `--resume`
- `--continue`
- `--quiet`

このうち、毎回の既定値にしたいものは `config.yaml` へ戻し、その回だけの明示的な上書きだけを CLI 引数で与える、という整理が重要です。

## 4-2. 毎回の依頼を定型化する

CLI が不安定になる最大の理由は、毎回の依頼が完全な自由記述だからです。うまくいく依頼には、たいてい共通の型があります。

- 失敗しているテストの原因候補を3つまで挙げる
- 指定した差分の保守性だけを見る
- 指定ファイルだけを修正する
- 指定 issue を要約して優先度候補を出す

この型が見えたら、依頼文を固定し、次に Skills へ切り出す候補として観察します。CLI は単なる会話手段ではなく、再利用可能な手順を見つけるための場でもあります。

## 4-3. 切り分け用の引数を活かす

CLI 利用で特に重要なのが、切り分け用の引数です。2026年5月14日時点の公式 docs でも、`--ignore-user-config` や `--ignore-rules` のような、普段の構成を外して再現を確認する導線があります。

これは障害切り分けで非常に役立ちます。

- profile 側の問題か
- `SOUL.md` や Context Files の問題か
- CLI 引数の問題か
- そもそも model / provider の問題か

実務では「うまくいかない」と感じたとき、通常構成を全部抱えたまま原因を探しがちです。しかし、それでは問題の層が見えません。余計な注入を外して最小構成で再現するかを見るほうが近道です。

## 4-4. 会話履歴へ依存しすぎない

CLI は便利なぶんだけ、会話履歴に頼りすぎやすい場所でもあります。途中でうまくいった依頼があると、そのまま長い session を延命したくなります。しかし実務では、「いまこの応答が良い」ことより、「明日同じことを再現できる」ことのほうが重要です。

そのため本書では、再利用したい前提は順に次のどこかへ移すことを勧めます。

- `config.yaml`
- `SOUL.md`
- Context Files
- Skills

会話履歴にだけ残した前提は、再現が難しく、切り分けにも弱いです。会話は観測の場であり、永続設定の置き場ではありません。

## 4-5. CLI で安定しない手順を常駐化しない

長時間運用へ広げる前に最も大事なのは、CLI で手順が安定していることです。CLI で毎回の依頼が揺れ、`--model` や `--skills` の付け方も一定せず、切り分け用の引数も使わない状態で Cron や Gateway へ進むと、問題は拡大するだけです。

CLI で確認すべき最低ラインは次です。

- 同じ仕事に対してだいたい同じ依頼文を使える
- どの profile を使うか説明できる
- 主要引数を毎回変えなくても済む
- 切り分け時に最小構成へ戻せる

`ForgeFlow` でも、最初に安定させるのは `coder` の CLI 利用です。Issue 監視や通知は、そのあとに `ops` へ足します。順番を守るだけで、かなり事故率が下がります。

## 4-6. この章のまとめ

CLI は単なる操作手段ではなく、成功する依頼の型と、壊れる条件を観測する場所です。ここで安定しないものを、そのまま Gateway や Cron へ広げてはいけません。主要コマンドと設定キーの対応は付録D、起動時だけ効く CLI / env 上書きは付録Hを引くと整理しやすくなります。次の章では、この CLI で見えてきた成功パターンをどう Skill として切り出すかを扱います。
