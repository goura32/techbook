# 4章 CLI を中心とした日常ワークフロー

Hermes Agent を実務へ入れるとき、最初の主戦場はやはり CLI です。常駐運用や複数チャネル連携は魅力的ですが、日常の開発では、まず「いま開いているリポジトリで何をどう頼むと安定するか」を掴むことが重要です。CLI はその感覚を作るのに向いています。会話、ファイル、テスト、差分確認が近い場所にあり、試行錯誤のコストも比較的低いからです。

ここで意識したいのは、毎回の依頼を全部自由記述で済ませないことです。毎回微妙に違う指示を出していると、うまくいった理由も失敗した理由も蓄積しません。日常ワークフローを安定させるには、「どういう種類の仕事を、どの profile へ、どの言い方で渡すか」を少しずつ固定していく必要があります。

たとえば `ForgeFlow` では、`coder` に対しては「失敗しているテストを読み、原因候補を 3 つまで挙げる」「差分の設計上の懸念だけを見る」「指定ファイルだけを修正する」といった依頼を定型化します。ここで大切なのは、最初から完了まで任せようとしないことです。AI エージェントに強いのは、曖昧な仕事ではなく、境界が見えている仕事です。

CLI 利用を続けると、会話ログや生成物の扱いも問題になります。どこまで会話履歴へ依存するか、途中の結論をどこへ残すか、やり直しのとき何を参照するか。これが曖昧だと、同じ依頼でも毎回温度感が変わります。だからこそ、CLI の日常利用では「会話に期待しすぎず、再利用したい前提は Skills や Context Files へ移す」ことが重要になります。

また、CLI は便利なぶんだけ、成功した体験から権限を広げすぎやすい場所でもあります。テストが通った、差分がきれいだった、よし次はもっと大きい仕事を任せよう、という流れは自然です。しかし、うまくいったタスクの性質を見ずに仕事のサイズだけを広げると、失敗時に責任範囲が曖昧になります。サイズを広げる前に、依頼の種類を分解したほうがうまくいきます。

日常ワークフローを整える目的は、将来の Gateway 運用や Cron 運用へそのまま延長することではありません。むしろ逆で、常駐運用へ行かなくても十分役立つラインをまず作ることです。CLI で安定しない手順を、そのまま常駐化しても問題は拡大するだけです。毎日の利用で、頼み方、観測点、止め方が見えてから次へ進みます。

この章で扱ったワークフローのうち、繰り返し始めたものは次の章で Skill に切り出します。つまり、CLI は単発利用の場所であると同時に、再利用可能な手順を見つける観測場所でもあります。次の章では、その Skill をどの粒度で作り、どう保守するかを整理します。
