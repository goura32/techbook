# Layout Review

## 目的

- 本文、図表、付録参照が同一見開きで詰まりすぎないかを確認する
- 電子書籍向けの作業メモと、紙面向けの本文表現を分ける

## 確認結果

### 1章

- `TaskHub` 紹介の直後に付録参照を置く流れは自然
- ただし、ファイルパス付きリンクのままだと書籍本文としてノイズが強いため、`付録 A` `付録 B` という参照表現へ変更した

### 4章

- `toTask()` の説明と図4-1の距離は適切
- 共通説明への参照は内部ファイルではなく、本文内の一般原則として言い換えた
- 付録 B 参照は、変換の流れを見返したくなる位置に絞れている

### 5章

- 図5-1の直前で package 境界の説明が十分に立っている
- 付録 A 参照は構造確認の補助として有効
- 本文ではファイルリンクを使わず、単純な付録参照へ統一した

### 6章

- CLI の全体像説明の直後に付録 B を案内する流れは自然
- 章頭で付録参照が先に出すぎないため、紙面の負荷は低い

### 7章

- `Task` から `TaskListItem` への変換例の直後に付録 B を置く流れは妥当
- 画面モデルの説明が主で、付録参照は補助に留まっている

### 9章

- root `tsconfig.json` の例と図9-1のつながりは自然
- 付録 A 参照は設定と構造の対応を見返す目的に合っている
- 本文では紙面向けに `付録 A` へ簡潔化した

## 反映した修正

- 本文中のローカルファイルリンクを削除し、`付録 A` `付録 B` 参照へ統一した
- 内部制作用ファイルへの直接言及を、本文で読める一般表現へ置き換えた

## 残課題

- 図表を実際に組版したあと、見開き内で図とコードブロックが連続しすぎないかを再確認する
- 付録に完全版サンプル断片を追加する場合、本文参照の回数が増えすぎないよう再評価する
