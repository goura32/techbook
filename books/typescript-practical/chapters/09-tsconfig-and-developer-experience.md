# 9. tsconfig と開発体験の設計

## この章で伝えること

- `tsconfig` と周辺ツールの組み合わせが、日々の開発効率をどう左右するかを整理する

## 節構成

### 9-1. `tsconfig.json` の最小構成を理解する

TypeScript の設定は広く、初めて見ると項目の多さに圧倒されます。ただし、実務で本当に大事なのは、すべてのオプションを暗記することではありません。`tsconfig.json` が何を決めているのかを、いくつかの責務に分けて理解することです。

大まかには、`tsconfig` は次のようなことを決めています。

- どのファイルを対象にするか
- どの厳しさで型検査するか
- どのモジュール解決方式を使うか
- どんな JavaScript を出力するか
- 補助情報として何を生成するか

この全体像が分かると、個々のオプションが単なる呪文ではなくなります。たとえば `strict` は型の厳しさに関わる設定、`moduleResolution` は import の解釈、`target` は出力 JavaScript の前提、`declaration` は配布向け型定義の生成、といった役割で読めるようになります。

新規プロジェクトでの最小構成は、機能を足す前に「何を基準にしているか」が分かることを優先したほうがよいです。設定が短いことそのものより、チームで説明できることのほうが大事です。

`TaskHub` のようなサンプルでも、`shared` `api-client` `cli` `web` で役割が違うため、ひとつの `tsconfig` だけですべてを雑に面倒を見るより、共通設定と個別設定を分けたほうが見通しがよくなります。

本書の Node.js 側は ESM を主例にしているため、`tsconfig` の説明でも `module: "nodenext"` を基準に考えます。これは「唯一の正解」という意味ではなく、2026年時点の新規 Node.js プロジェクトで前提をそろえやすい基準だ、という意味です。

### 9-2. 厳しさをどこまで上げるか

`strict` を有効にするかどうか、あるいはその周辺オプションをどこまで強くするかは、多くのチームが悩むところです。理想だけを言えば厳しいほうが安全ですが、既存コードベースや導入段階によっては、一気に上げると現場が回らなくなることもあります。

ここで大切なのは、「厳しさを上げること」が目的ではなく、「曖昧さを減らして変更しやすくすること」が目的だと忘れないことです。たとえば `strictNullChecks` は、面倒に見えても実務効果が非常に大きい設定です。一方で、あるオプションはチームの現在地によっては後回しでも構わない場合があります。

判断のしかたとしては、次の問いが役立ちます。

- その設定はどの種類の事故を減らすか
- 導入コストは一時的か、恒常的か
- 既存コードの修正負担はどれくらいか
- チーム全体で運用できるか

実務では、`strict` を起点にしつつ、どうしても難しい箇所だけ明示的に逃がすほうが、緩い設定から必要な項目を後で積むよりも管理しやすいことがあります。もちろん既存資産の事情もあるため、最終的には「理想の設定」より「継続できる設定」のほうが重要です。

### 9-3. monorepo と project references

TypeScript のコードベースが大きくなると、ひとつの `tsconfig.json` だけでは管理しきれなくなります。そこで出てくるのがモノレポ構成や `project references` です。これらは単なる高速化のための仕組みではなく、ビルド境界と責務境界を整理する助けになります。

`project references` を使うと、複数パッケージや複数アプリケーションの型検査とビルド関係を明示できます。どこがどこへ依存するかが見えやすくなり、大規模化したときの待ち時間や再ビルド範囲も制御しやすくなります。

ただし、ここでも注意したいのは「物理的な分割」と「設計上の分割」を混同しないことです。references を張ったから設計がよくなるわけではありません。5章で見たように、公開 API と依存方向が整っていて初めて、こうした仕組みが活きます。

実務では次のような順で考えると整理しやすいです。

1. まず責務ごとの分割を考える
2. その分割に沿って package や app の境界を置く
3. そのうえで project references を使う

ツールチェーンの都合で無理に細かく分けると、逆に設定の複雑さだけが増えることがあります。分割の目的が「速さ」なのか「責務分離」なのかを常に意識しておくと、ぶれにくくなります。

`TaskHub` を例にすると、たとえば `shared` と `api-client` を `packages/`、`cli` と `web` を `apps/` に置き、それぞれに `tsconfig.json` を持たせつつ、ルートで references を束ねる構成が考えられます。こうすると、どの package がどこへ依存しているかが設定上も見えやすくなります。

たとえば Node.js 側の共通設定では、次のように `nodenext` を土台に置く考え方が自然です。

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "strict": true
  }
}
```

このとき大事なのは、`nodenext` を入れたら終わりではないことです。`package.json` の `"type": "module"`、実行コマンド、出力先、テスト環境まで含めて前提をそろえて、はじめて設定の意味が揃います。

ルートの `tsconfig.json` は、たとえば次のような形から始められます。

```json
{
  "files": [],
  "references": [
    { "path": "./packages/shared" },
    { "path": "./packages/api-client" },
    { "path": "./apps/cli" },
    { "path": "./apps/web" }
  ]
}
```

この構成にしておくと、`shared` の変更がどこへ波及するか、`web` が `api-client` を通るべきなのか、といった依存の輪郭が設定ファイルにも現れます。モノレポでは「動けばよい」設定より、「依存の方向が見える」設定のほうが長く効きます。構造そのものを見返したいときは、付録 A と往復すると理解しやすくなります。

### 9-4. ESLint、Formatter、editor 設定との整合

TypeScript の開発体験は、`tsconfig` 単体では決まりません。実際には ESLint、Formatter、エディタ補完、保存時自動修正、import 整理などが組み合わさって、日々の快適さが決まります。

ここでありがちな失敗は、複数のツールが似た責務を取り合ってしまうことです。たとえば、型の問題を ESLint で見ようとしすぎたり、整形と意味チェックの責務が曖昧だったりすると、設定は増えるのにチームの理解は追いつかなくなります。

実務では、次のように役割を分けると整理しやすいです。

- TypeScript: 型整合性とモジュール解決
- ESLint: 書き方や危険なパターンの検出
- Formatter: 文字面の統一
- editor: 補完、ジャンプ、軽い自動修正

この分離があると、「どの警告をどこで直すか」が明確になります。また、CI へ持ち込むべきものと、ローカルだけで済ませるものの切り分けもしやすくなります。

TypeScript の導入で開発体験が良くなるかどうかは、型が強いかどうかだけではなく、「チーム全員が同じ前提で編集できるか」に強く依存します。その意味で、editor 設定まで含めた一貫性はかなり重要です。

`TaskHub` のように複数 package がある場合は、どの package を開いても同じ補完品質と同じ診断基準になるようにしておくことが特に大事です。片方では `strict`、もう片方では緩い、という状態はすぐに負債になります。

### 9-5. 大規模化したときの遅さと向き合う

TypeScript の運用で避けて通れないのが、規模が大きくなったときの遅さです。型チェックの待ち時間、エディタ補完の重さ、ビルド時間、CI 時間が積み重なると、開発体験はじわじわ悪化します。

ここで重要なのは、遅さを「仕方ないもの」と諦めないことです。多くの場合、遅さには理由があります。巨大な union、過剰に複雑な条件型、境界のない import、全部入りの `tsconfig`、責務の曖昧な package 分割など、設計上の要因が性能へ跳ね返っていることがよくあります。

改善の観点としては、少なくとも次のようなものがあります。

- 型を複雑にしすぎていないか
- build と typecheck の責務を分けられないか
- package 境界や references を見直せないか
- editor が不要な範囲まで解析していないか
- 新しいツールチェーンへの移行価値があるか

2026年時点では、TypeScript 6.x / 7.x の流れもあり、速さそのものが大きなテーマになっています。ただし、ツール更新だけで解決しない問題も多く、コードベース側の設計改善が必要なことは少なくありません。

開発体験は贅沢品ではなく、生産性の基盤です。遅さを単なるストレスとして片付けず、設計とツールチェーンの両面から向き合うことが、長期運用では重要になります。

`TaskHub` のような小さめのモノレポでも、`web` の editor 応答、`cli` の型検査時間、`shared` の変更がどこまで再ビルドを引き起こすかを見るだけで、ツールチェーン設計の勘所がかなり分かります。

たとえば `packages/shared/tsconfig.json` では、次のように責務を絞った設定が考えられます。

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "rootDir": "./src",
    "outDir": "./dist",
    "declaration": true,
    "declarationMap": true
  },
  "include": ["src/**/*.ts"]
}
```

この例では、`shared` を「他の package から参照される安定した土台」として扱っています。`web` 側の設定では JSX や bundler 寄りの都合が増えますが、基盤となる package まで同じ前提に引きずらないほうが、設定の意図が読みやすくなります。

一方で、既存システムや古い依存関係の都合で CJS を維持する現場もあります。その場合でも、本書としては CJS を主例にはしません。CJS は「移行時に何が違うか」「なぜ `nodenext` と `"type": "module"` を意識する必要があるか」を理解するための比較対象として扱うほうが、章全体の筋が通ります。
