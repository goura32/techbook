# 8. テスト、ビルド、デバッグ

## この章で伝えること

- 型検査とテストの役割を混同せず、開発体験を壊さない構成を示す

## 節構成

### 8-1. 型検査、単体テスト、E2E の役割分担

TypeScript を導入すると、ときどき「型があるならテストは減らせるのではないか」という期待が生まれます。これは半分正しく、半分危険です。たしかに TypeScript は、引数の型違い、存在しないプロパティ参照、網羅漏れの一部を防いでくれます。しかしそれは、「コードが意図した仕様を満たしているか」を確認することとは別です。

型検査が得意なのは、次のような問題です。

- 関数契約の破れ
- `null` や `undefined` の扱い漏れ
- モジュール間の不整合
- 判別可能 union の取りこぼし

一方で、テストが必要なのは次のような問題です。

- 実装ロジックが仕様通りか
- 複数の値の組み合わせで期待どおりに動くか
- 外部 API や DB とつないだときに破綻しないか
- UI 操作を通したときに表示と状態が一致するか

E2E テストはさらに別の役割を持ちます。実際の画面遷移、フォーム送信、認証フロー、重要なユーザーストーリーを守るのが仕事です。型検査や単体テストで十分な場面もありますが、「ユーザーから見て壊れていないか」という確認には代わりません。

TypeScript の実務では、型検査を「テストの代わり」と考えるより、「テストを書く前に落とせるものを先に落とす層」と考えるほうが自然です。そうすると、型検査とテストは競合せず、むしろお互いの役割がはっきりします。

`TaskHub` で考えるなら、たとえば次のような分担になります。

- 型検査: `Task` と `TaskListItem` の契約崩れを防ぐ
- 単体テスト: `toTask()` や `toTaskListItem()` の変換結果を確認する
- 統合テスト: `fetchTasks()` が異常系をどう扱うかを見る
- E2E: `web` でタスク一覧が正しく見えるかを確認する

### 8-2. テストで型に頼るところ、頼らないところ

テストを書くときにも、TypeScript の型は助けになります。たとえばテストデータの形が本番コードとずれていないか、モックの戻り値が関数契約を守っているか、期待している API の呼び出し方が正しいか、といった点は型があると崩れにくくなります。

ただし、型に頼りすぎると、テストの意図が薄くなることがあります。典型例は、「型が通っているから正しいはずだ」と思って、境界条件や失敗ケースを十分に書かなくなることです。

```ts
type Discount = {
  kind: "fixed" | "rate";
  value: number;
};
```

この型が正しくても、`rate` が `200` だったらどうするのか、負の値はどう扱うのか、複数割引の適用順はどうするのか、といった仕様上の判断までは守ってくれません。

テストで型に頼ってよいのは、「書き間違いを減らすこと」です。頼りきってはいけないのは、「仕様判断まで代替してもらうこと」です。実務では、次のように使い分けると整理しやすくなります。

- 型に頼る: テストデータの形、モックの契約、補完による誤記防止
- テストで確認する: ビジネスルール、境界条件、失敗ケース、実際の振る舞い

つまり、型はテストを薄くするためではなく、テストを正確に書きやすくするためにあります。

たとえば `TaskHub` の `toTask()` には、型だけでは守れない確認があります。`due_at` が `null` のとき `dueAt` が `null` になるか、担当者がいないとき `assigneeName` が `null` になるか、といった点は単体テストで押さえる価値があります。

### 8-3. ソースマップとデバッグ体験

TypeScript のデバッグ体験は、最終的には「実行時に何が見えるか」で決まります。ここで大きく効くのがソースマップです。TypeScript をビルドして JavaScript に変換したあとでも、元の `.ts` ファイルの位置でスタックトレースやブレークポイントを見られるようにする仕組みです。

ソースマップが正しく機能していないと、エラー位置がビルド後の JavaScript を指し、行番号もずれて、調査の負担が一気に上がります。実務では「とりあえず動く」より、「壊れたときに追える」ことのほうが長く効きます。

Node.js 側でもフロントエンド側でも、次の点は早めに確認しておいたほうがよいです。

- 開発時にソースマップが有効か
- 本番ログやエラー監視で元ソースに辿れるか
- bundler や minify の影響で追跡不能になっていないか
- テスト失敗時のスタックトレースが読めるか

デバッグ体験は、`tsconfig` だけで決まるわけではありません。実行ランタイム、bundler、テストランナー、IDE の組み合わせで決まります。そのため、「どこで TypeScript が実行され、どこで JavaScript へ変換されるか」を把握しておくことが重要です。

実務の観点では、最初から完璧なデバッグ環境を目指すより、「エラー時に人が辿れる」状態を作ることを優先するとよいです。そこが整っていれば、ツール更新にも追従しやすくなります。

### 8-4. bundler、transpiler、type checker の分離

TypeScript の周辺ツールを理解するとき、混乱を減らす一番のコツは、役割を分けて見ることです。とくに次の 3 つは別物として考えたほうが整理しやすくなります。

- type checker: 型整合性を検査する
- transpiler: TypeScript を JavaScript へ変換する
- bundler: モジュールをまとめて出力を最適化する

ひとつのツールが複数の役割を持つこともありますが、頭の中で役割を分離しておくと「どこで何が起きているか」を把握しやすくなります。

たとえば、ビルドが速いからといって、それだけで型検査が十分とは限りません。逆に、型検査が通ったからといって、出力形式や tree shaking が期待通りとは限りません。役割を混同すると、問題の切り分けが難しくなります。

実務では、次のような構成がよくあります。

- 開発時は高速な transpiler や実行ツールを使う
- CI や本番ビルド前には `tsc --noEmit` で型検査する
- bundler は配布や本番出力の責任を持つ

この分離ができていると、速さと安全性のバランスを取りやすくなります。逆に、全部をひとつの魔法のツールに任せると、設定が見えにくくなり、トラブル時の説明責任も持ちにくくなります。

`TaskHub` でも、`web` は bundler 前提、`cli` は Node.js 実行前提、`shared` は型検査中心というように役割が違います。同じ TypeScript でも、すべてを同じビルド経路で考えないほうが整理しやすくなります。

### 8-5. CI で落とすべきものを決める

TypeScript の導入効果は、ローカル開発だけでなく CI にも現れます。ただし、何でもかんでも CI で走らせればよいわけではありません。時間がかかりすぎると無視され、厳しさがばらつくと信頼されません。

まず決めたいのは、「CI で絶対に落とすもの」と「ローカルで補助的に見るもの」の区別です。たとえば次のような整理が考えられます。

- 必須: 型検査、Lint、単体テスト
- 条件付き: E2E、契約テスト、重い統合テスト
- 補助: サイズ計測、速度計測、warning 集計

大切なのは、CI がチームの共通基準になることです。誰かのローカル環境でだけ通る設定は、実務では価値が低いです。TypeScript では特に、`tsconfig` の差分、Node.js バージョン差分、モジュール解決方式の差分がトラブルの原因になりやすいため、CI 側で基準を固定しておく意味が大きくなります。

また、CI では「何が落ちたのかが分かる」ことも重要です。型検査、Lint、テストが全部まとめて一気に失敗するより、段階ごとに分かれていたほうが原因を追いやすいことがあります。厳しさだけでなく、調査しやすさも設計の一部です。

`TaskHub` のように `shared / api-client / cli / web` が分かれているときは、少なくとも `shared` の型検査、変換ロジックの単体テスト、`web` の主要画面 E2E をどこまで必須にするかを決めておくと、CI の意味がはっきりします。

たとえば `TaskHub` なら、CI の流れは次のように分けられます。

```yaml
jobs:
  typecheck:
    steps:
      - run: pnpm tsc -b --pretty false
  test-unit:
    steps:
      - run: pnpm vitest run
  test-e2e:
    steps:
      - run: pnpm playwright test
```

重要なのは YAML の書き方そのものではなく、失敗の種類を分離することです。型の崩れなのか、変換ロジックの不具合なのか、画面操作を含む回帰なのかが分かれていれば、修正の入り口がかなり見つけやすくなります。

また、`toTask()` や `toTaskListItem()` のような変換関数は、見た目以上にテスト効率が高い場所です。外部入力の揺れと内部モデルの安定性がぶつかる場所だからこそ、境界条件を少数のテストで密に押さえやすくなります。

この章で見てきたのは、TypeScript の周辺にある検査と実行の仕組みです。次章では、その中心にある `tsconfig` と日々の開発体験へ焦点を当てます。
