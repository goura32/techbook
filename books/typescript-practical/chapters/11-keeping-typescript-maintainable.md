# 11. 継続運用で壊れない TypeScript

## この章で伝えること

- 書き始めた後に崩れないための運用原則をまとめる

## 節構成

### 11-1. 破壊的変更を小さく閉じ込める

TypeScript のコードベースは、最初に整っていても、そのままでは保てません。機能追加、依存更新、チーム拡大、設計変更を繰り返す中で、少しずつ前提が崩れていきます。継続運用で大切なのは、変化そのものを止めることではなく、破壊的変更の影響範囲を小さく閉じ込めることです。

そのためには、まず境界を厚く持つことが重要です。4章から7章で見てきたように、外部入力、公開 API、画面モデル、設定型が分かれていれば、変更はその境界で吸収しやすくなります。逆に、すべてがそのままつながっていると、小さな変更がコードベース全体へ波及します。

破壊的変更を小さくするための実務上の原則としては、次のようなものがあります。

- 公開型をむやみに広げない
- 変換層を省略しない
- 内部実装を直接 export しない
- optional や union の意味を曖昧にしない

TypeScript は広いリファクタリングに強い一方で、型定義そのものが API になるため、無邪気に広げた型ほど後で足かせになります。保守しやすさとは、「変更しやすいこと」だけではなく、「変更の影響が予測しやすいこと」でもあります。

### 11-2. バージョン更新のルールを作る

TypeScript を使うコードベースでは、更新対象が多くなります。TypeScript 本体、Node.js、ESLint、テストランナー、bundler、型定義パッケージ、フレームワーク。これらを場当たり的に更新していると、どこで何が壊れたのか追えなくなります。

そこで必要なのが、更新のルールです。たとえば、

- TypeScript 本体の更新は月次か四半期ごとか
- beta や preview はどの環境で試すか
- major 更新を誰が判断するか
- 型定義更新をアプリ更新と一緒にやるか分けるか

といったルールがあるだけで、更新の負担はかなり軽くなります。

実務では「常に最新が正しい」とは限りません。一方で、古いまま放置すると差分が大きくなり、後で一気に苦しくなります。大切なのは、更新をイベントではなく習慣にすることです。小さく継続的に更新しておくほうが、長く止めたあとに大移行をするより安全です。

このとき、更新の成否を人の感覚だけで判断しないことも大切です。CI、ビルド時間、型エラー件数、主要ユースケースの動作確認など、最低限の観測指標を持っておくと、更新判断が安定します。

### 11-3. 型定義の負債を返済する

TypeScript のコードベースで蓄積しやすい負債には、実装負債とは少し違う種類があります。典型的なのは、次のようなものです。

- 残り続ける `any`
- 意味の曖昧な `unknown` の放置
- 使われなくなった union の選択肢
- 何層も重なった utility types
- 実態とずれた型エイリアス

これらはコードが動いている限り放置されがちですが、将来の変更コストを確実に上げます。特に危険なのは、「型があるので安心」と見えるのに、実際には信用できない状態です。型の見た目が整っているほど、読む人は安心してしまいます。

負債返済で有効なのは、大掃除ではなく局所的な改善です。たとえば、

- 新しく触る箇所の `any` を減らす
- 境界にアサーションが続いている場所を変換関数へ寄せる
- 意味のない共通型を具体的な名前へ分ける
- 実際に使われていない型 export を閉じる

といった改善を、日常的な変更のついでに進めるほうが現実的です。

型の負債は、コードレビューでも見つけやすい領域です。「なぜこの `any` が必要なのか」「この union は本当に必要か」「この `Pick` の元型に依存し続けるべきか」といった問いを、レビューの観点へ入れておくと少しずつ改善が進みます。

### 11-4. レビューで見るべきポイント

TypeScript のレビューでは、文法エラーや型エラーの有無だけを見ても足りません。むしろ本当に見るべきなのは、「その型の置き方が設計として妥当か」です。

実務でレビュー時に確認したい観点は、次のようなものです。

- その型は境界を明確にしているか
- API レスポンス型と内部型が混ざっていないか
- `any` やアサーションは局所化されているか
- optional や `null` の意味が揺れていないか
- 公開 API が広がりすぎていないか

また、型が複雑すぎるときは、「正しいか」だけでなく「読めるか」も重要です。TypeScript では、技術的に表現できることと、チームが長く保守できることは別です。条件型や mapped types が何重にも重なっているなら、型のかっこよさより、説明可能性を優先したほうがよい場合があります。

レビューの観点を共有しておくと、型の品質は個人依存になりにくくなります。これは 9章で見た editor や CI と同じで、「誰が見ても同じ方向へ判断できる仕組み」を作ることが運用の安定につながります。

### 11-5. チームで設計原則を共有する

最終的に、継続運用で一番効くのはチームの共通理解です。TypeScript は強力ですが、使い方の自由度も高いため、チーム内で前提がばらばらだとすぐに書き方が散らかります。

たとえば、次のような原則が共有されているだけで、コードベースの安定性は大きく変わります。

- 外部入力は `unknown` から始める
- API 型と内部型は分ける
- `strict` を前提に考える
- `any` は理由が説明できる場所だけに置く
- export は最小限に保つ

これらは大げさな設計規約でなくても構いません。`README`、設計メモ、テンプレート、レビュー観点、サンプル実装など、いくつかの形で残っていれば十分です。重要なのは、暗黙知にしないことです。

TypeScript を導入しても、チームの原則が共有されていなければ、数か月で「型はあるが読みにくいコードベース」になってしまいます。逆に、完璧な型テクニックがなくても、原則が共有されていれば、変更に強く読みやすいコードベースへ育てられます。

本書全体で繰り返してきたのは、TypeScript を「型を書くための言語」としてではなく、「境界と責務を整理し、変化に耐えるための言語」として使う視点です。新機能やツールチェーンは今後も変わりますが、この視点は比較的古びにくいはずです。読者がこの視点を持って日々の実装とレビューへ戻れるなら、本書の目的は果たせたと言えます。

## 実務チェックリスト

### 更新前チェック

- TypeScript 本体、Node.js、Lint、test runner の依存関係が整理されているか
- CI とローカルで同じ TypeScript バージョンを前提にしているか
- ロールバック手順があるか
- 主要ユースケースで確認する観測項目が決まっているか

### レビュー時チェック

- 境界で `unknown` や検証が省略されていないか
- API 型と内部型が混ざっていないか
- `any` や `as` が局所化されているか
- optional や `null` の意味が揺れていないか
- export が必要以上に広がっていないか

### 型負債チェック

- 残っている `any` に理由があるか
- 使われていない型 export が残っていないか
- utility types が読みやすさを損ねていないか
- アサーションが変換層ではなく利用側へ漏れていないか
- 変更時に壊れやすい union や optional が放置されていないか
