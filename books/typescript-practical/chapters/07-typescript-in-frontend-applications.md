# 7. フロントエンドでの実践

## この章で伝えること

- フロントエンドで TypeScript が本当に効く場所を見極める

## 節構成

### 7-1. UI コンポーネントにおける型の責務

フロントエンドで TypeScript を使っていると、型が最も目に見えやすいのはコンポーネント定義です。props の型、イベントハンドラの型、state の型がすぐに現れるため、つい「フロントエンドの TypeScript とは props を正しく書くことだ」と考えがちです。しかし、実務で本当に重要なのは、コンポーネントがどこまで責務を持つかを曖昧にしないことです。

コンポーネントが担うべき役割は、基本的には表示とユーザー操作の受け取りです。ところが、実際にはそこへ API レスポンスの揺れ、フォームの検証、画面遷移条件、権限ロジック、画面ローカルの一時状態などが集まりやすくなります。その結果、props が巨大になり、型は付いていても何を表しているのか分かりにくくなります。

`TaskHub` では、この章の対象は `web` です。4章で見た一般原則を繰り返すのではなく、すでに変換済みの内部モデルを UI へどう渡すか、どこから画面固有の state が増えるのかに焦点を当てます。

`TaskHub` の `web` では、`Task` をそのまま props に渡す場面もありますが、一覧画面や編集画面では、さらに表示都合の画面モデル（view model）へ寄せたほうがよいことがあります。たとえば、期日表示や担当者ラベルのような「画面で毎回同じ変換をするもの」は、画面手前で整えておくと UI が軽くなります。

```ts
type UserCardProps = {
  user: {
    id: string;
    displayName: string | null;
    email: string | null;
    role: "admin" | "member";
    isLoading?: boolean;
    isSelected?: boolean;
    canEdit?: boolean;
  };
  onSelect?: (id: string) => void;
  onSave?: (data: unknown) => Promise<void>;
};
```

このような props は、一見すべて型付けされていても、責務が混ざっています。表示用のデータ、画面状態、権限制御、保存操作が同居しているため、コンポーネントの役割がぼやけます。

よりよい方向は、UI コンポーネントに渡す責務を絞ることです。たとえば、

- 表示に必要な値だけを渡す
- 画面ロジックは親または専用の層へ寄せる
- 保存処理や API 境界は UI の手前で吸収する

という方針を取ると、props の型は読みやすくなります。

TypeScript はここで「何でも厳密に書く道具」ではなく、「責務が多すぎることに気づく道具」として使えます。props が長くなりすぎたら、それは型の問題である前に設計の問題かもしれません。

### 7-2. props と state をどう絞るか

フロントエンドのコンポーネントは、外から受け取る props と、自分で持つ state の両方を扱います。この 2 つをどう分けるかは、見た目以上に重要です。型が付いていても、この境界が曖昧だとコンポーネントはすぐに複雑になります。

props は「外から与えられるもの」、state は「そのコンポーネントが内部で管理するもの」と考えると分かりやすいですが、実務ではその中間が多く現れます。たとえば、API から来た値をそのままフォーム state に流し込むのか、編集用モデルへ変換してから持つのかで設計は変わります。

state 設計でありがちなのは、「いま必要そうなもの」をそのまま全部持つことです。

```ts
type PageState = {
  isLoading: boolean;
  isSaving: boolean;
  errorMessage: string | null;
  selectedUserId: string | null;
  users: User[];
  filteredUsers: User[];
  searchText: string;
};
```

このような state は、最初は便利でも、派生可能な情報まで保存し始めると同期ズレの原因になります。`filteredUsers` のように `users` と `searchText` から計算できるものは、必ずしも state に置く必要はありません。

TypeScript は、state の値を厳密にするだけでなく、「それは本当に独立した状態か」を考えるきっかけにもなります。実務では次の観点が有効です。

- 外から来た値をそのまま持つべきか
- 計算で求まる値まで state に含めていないか
- `null` や optional を増やしすぎていないか
- 成功、失敗、読み込み中を別々のフラグで持ちすぎていないか

とくに `isLoading`、`data`、`error` をばらばらに持つより、状態全体を判別可能 union で持つほうが明快なことがあります。

```ts
type UsersState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; users: User[] }
  | { status: "error"; message: string };
```

この形にすると、描画ロジックと型の分岐が一致しやすくなります。2章で見た narrowing が、フロントエンドでもそのまま効いてきます。

### 7-3. API クライアントと画面層の境界

フロントエンドで TypeScript の恩恵が最も大きいのは、実はコンポーネント内部よりも API クライアントと画面層の間です。ここを丁寧に切ると、外部仕様の揺れが UI へ直接流れ込むのを防げます。

悪い例は、API レスポンスをそのまま画面で使うことです。

```ts
type ApiUser = {
  id: string;
  display_name: string | null;
  avatar_url?: string;
};
```

この `ApiUser` をそのままコンポーネントに渡すと、画面側は `display_name` や optional な `avatar_url` の事情を知る必要が出てきます。結果として、画面は外部 API の都合に引っ張られます。

よりよい設計は、API 層で一度変換し、画面で使いやすいモデルへ整えることです。

```ts
type UserViewModel = {
  id: string;
  displayName: string;
  avatarUrl: string | null;
};
```

この `UserViewModel` は、画面が必要とする都合だけで設計されています。`null` をどう扱うか、フィールド名をどう統一するか、表示に必要なデータをどこまで整形するかを API 層の近くで決めておけば、UI 側の条件分岐は減ります。

この境界でのポイントは、次の通りです。

- API の型と画面の型を同一視しない
- 変換をどこで行うかを固定する
- 画面へ渡す時点で意味の揃ったモデルにする

TypeScript は、変換前と変換後の型を分けて持てるため、この設計に向いています。型が複数あることを面倒に感じるかもしれませんが、その複数性こそが境界を守っています。

`TaskHub` の一覧画面向けには、たとえば次のような view model を作れます。

```ts
type TaskListItem = {
  id: string;
  title: string;
  statusLabel: string;
  dueLabel: string;
  assigneeLabel: string;
};

function toTaskListItem(task: Task): TaskListItem {
  return {
    id: task.id,
    title: task.title,
    statusLabel: task.status === "open" ? "未完了" : "完了",
    dueLabel: task.dueAt ? task.dueAt.toLocaleDateString() : "期限なし",
    assigneeLabel: task.assigneeName ?? "未割り当て",
  };
}
```

この `TaskListItem` を渡しておけば、UI コンポーネントは「表示に必要な文字列」を扱うだけで済みます。もちろん、すべてを文字列へ落とす必要はありませんが、少なくとも API の都合を画面へ直接持ち込まないことが重要です。`Task` から `TaskListItem` へのつながりをあとで見返したいときは、付録 B が役に立ちます。

### 7-4. フロントエンドで増えやすい `any` を減らす

フロントエンドでは、`any` が増える入口がいくつかあります。たとえば次のような場所です。

- `fetch()` や外部 SDK のレスポンス
- フォームライブラリのイベントや値
- 汎用 UI コンポーネントの props
- `window` や DOM 関連の拡張
- 急いで書いた一時的な変換関数

これらは「今はよく分からないから `any` で逃がす」という判断がしやすく、しかも UI ではすぐに表示が確認できるため、問題が後回しになりやすいです。ところが `any` が増えると、画面ロジックの refactor が急に怖くなります。

`any` を減らすときの基本方針は、全部を一気に厳密化することではありません。次の順番が現実的です。

1. 外部入力を `unknown` で受ける
2. 境界で型を確定する
3. UI 内部ではアサーションを増やさない

たとえば、`event: any` と書くよりも、まずはイベントハンドラの責務を狭めるほうが有効な場合があります。汎用コンポーネントでも、受け取る値の型変数を意味のある範囲に限定すれば、`any` なしで十分表現できることが多いです。

また、`as SomeType` が連続している場所は、だいたい境界の責務が曖昧です。アサーションを悪と決めつける必要はありませんが、繰り返し現れるなら「ここでちゃんと変換層が足りないのではないか」と疑ったほうがよいです。

### 7-5. フレームワーク依存を増やしすぎない設計

2026年時点のフロントエンド開発では、React 系を中心に多くの実務コードが書かれています。ただし、本書はフレームワーク本ではないため、ここで大切にしたいのは「どのフレームワークでも比較的通用する設計原則」を抽出することです。本書では、フレームワーク固有の hook やコンポーネント API へ深入りする代わりに、その手前にある画面モデル、状態遷移、境界設計を主題に置きます。

フレームワーク依存が強くなりすぎると、TypeScript の説明がそのまま React や Next.js の書き方に吸収されてしまいます。それ自体は悪くありませんが、本書の価値である「技術の輪郭」をぼかしてしまいます。

そのため、本書では次のような原則を優先します。

- 画面層とデータ境界を分ける
- UI state とドメインデータを混ぜない
- API レスポンスをそのまま props にしない
- 成功、失敗、読み込み中の状態を明示する
- フレームワークの便利機能より、責務分離を先に考える

React を例に説明する場面はあっても、そこで示したいのは hook の書き方ではなく、状態と境界の設計です。たとえば `useState`、`useReducer`、サーバーコンポーネント、ルーター連携などは、すべて「どこで値の意味を変えるか」「どこで失敗を受け止めるか」という同じ問いへ戻せます。本書のフロントエンド章は、特定フレームワークの最適解を配るのではなく、どの UI 技術を選んでも流用しやすい判断軸を残すことを優先します。

フロントエンドで TypeScript をうまく使うとは、型が付いていることではなく、UI の責務が見えることです。次章では、この考え方を支えるテスト、ビルド、デバッグへ進みます。
