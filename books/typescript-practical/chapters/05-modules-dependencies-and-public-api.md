# 5. モジュール、依存関係、公開 API 設計

## この章で伝えること

- 大きくなっても崩れにくい TypeScript の分割単位を示す

## 節構成

### 5-1. import/export とモジュール境界

TypeScript のコードベースが大きくなると、型の難しさ以上に効いてくるのが、モジュールの切り方です。どのファイルが何を持ち、何を外へ見せ、どこまでを内部実装として隠すか。この境界が曖昧だと、型の整ったコードでも保守は苦しくなります。

`import` と `export` は単なる文法ではなく、依存方向を決めるための道具です。どこからでも何でも import できる状態は、一見便利でも、変更の影響範囲を広げます。逆に、モジュールごとの責務が明確で、公開面が限定されていると、内部実装を安心して入れ替えやすくなります。

たとえば、ユーザー関連の処理をまとめるとき、次の 2 つは似ているようでかなり違います。

```ts
// users/index.ts
export * from "./types";
export * from "./repository";
export * from "./service";
export * from "./validation";
```

```ts
// users/index.ts
export { createUser, getUser } from "./service";
export type { User, CreateUserInput } from "./types";
```

前者は何でも外へ出す設計です。後者は利用者に使ってほしい面を選んでいます。実務では、後者のように公開面を絞るほうが、モジュール境界は安定しやすくなります。

モジュール境界で意識したいのは、次の 3 点です。

- 内部実装を外へ漏らさない
- 利用者に見せたい契約だけを出す
- 依存の入口を少なくする

型が豊富に書ける TypeScript では、つい「型定義だけなら出してもよい」と考えがちです。しかし、型も API の一部です。外へ出した型は、後で変更しにくくなります。型を export することは、将来の保守コストを引き受けることでもあります。

`TaskHub` でこれを考えると、たとえば `shared` パッケージが何を export するかが論点になります。`Task` のような内部モデルは共有したいかもしれませんが、`TaskApiResponse` のような外部 API 都合の型まで `shared` から公開すると、`web` や `cli` が外部仕様へ直接依存し始めます。共有したいのは「安定した内部契約」であって、「揺れやすい外部境界」ではありません。

### 5-2. 内部 API と公開 API を分ける

実務でありがちな問題のひとつは、モジュール内部で都合よく作った型や関数が、そのまま別のモジュールから使われ始めることです。最初は「ちょっと使いたいだけ」でも、時間が経つとそれが暗黙の公開 API になります。

```ts
// users/service.ts
export function normalizeEmail(value: string): string {
  return value.trim().toLowerCase();
}
```

この関数は便利ですが、本来は `users` モジュールの内部実装かもしれません。ところが export されていると、他の場所からも使われ始め、`users` ドメインに閉じた変更が難しくなります。

公開 API と内部 API を分ける感覚は、ライブラリ開発だけでなくアプリケーション開発でも重要です。明示的に export するものは、「他の人に依存してほしいもの」だと考えると判断しやすくなります。

実務では、次のような層で API を考えると整理しやすいです。

- モジュール内部だけで使う実装関数
- 同じ機能群の中で共有する内部 API
- 他モジュールへ見せる公開 API
- 外部パッケージとして見せる公開 API

この区別があると、たとえば `normalizeEmail()` を内部専用に保ちつつ、外へは `createUser()` だけを見せる、といった設計がしやすくなります。TypeScript では型定義も含めて API になるため、「何を外へ見せるか」の判断は JavaScript より一段重いと考えたほうがよいです。

`TaskHub` でも同じで、`api-client` の内部にある `toTask()` やレスポンス検証関数は、便利でもそのまま `web` から import できる形にしないほうが安全です。外へ見せるのは `fetchTasks()` や `Task` のような、利用者に依存してほしい面に絞るほうが長期運用では強くなります。

### 5-3. 依存方向を制御する

モジュールが増えると、問題は「どこから import できるか」に移ります。依存方向が整理されていないコードベースでは、UI から DB 層を直接呼んだり、ドメイン層がプレゼンテーション層の型に依存したりといった逆流が起こります。

依存方向の基本は、「より内側のものは、外側の都合を知らない」ことです。たとえば次のような流れは、理解しやすい構造です。

- UI 層がアプリケーション層を呼ぶ
- アプリケーション層がドメイン層を呼ぶ
- インフラ層がインターフェースを実装する

逆に、ドメイン層が React コンポーネント用の型や HTTP レスポンス型へ直接依存し始めると、責務が混ざります。

TypeScript では import が簡単なので、構造の崩壊も静かに起こります。だからこそ、「どこからどこへ依存してよいか」を設計ルールとして持っておくことが大切です。ツールで補助することもできますが、その前に言語化が必要です。

判断基準としては、依存する側が「相手の実装都合」を知りすぎていないかを見るとよいです。型が rich だからといって詳細な内部型を共有しすぎると、見た目の型安全さと引き換えに、変更容易性を失います。

`TaskHub` の場合、`web` が `api-client/internal/normalize-task.ts` のような深いパスへ依存し始めたら、すでに危険信号です。5章の話は抽象論ではなく、こうした import 経路の癖として現れます。

### 5-4. ライブラリ設計で壊れやすいポイント

TypeScript でライブラリや共有パッケージを作るとき、最も壊れやすいのは実装よりも公開面です。特に問題になりやすいのは、次のような要素です。

- 型引数の数や意味
- union の選択肢
- optional property の有無
- export している内部型
- 便利そうに見える再 export

たとえば、最初は内部都合で追加したプロパティでも、一度型として公開すると利用者が依存し始めます。その結果、実装の自由度が下がります。JavaScript より TypeScript のほうがこの問題が起きやすいのは、型が IDE 補完やドキュメントとして非常によく見えるからです。

壊れやすさを減らすには、公開 API を「小さく、意味がはっきりしたもの」に保つのが基本です。便利だからといって低レベル関数をそのまま export するのではなく、本当に長く支える覚悟のある面だけを公開します。

また、公開 API では「推論が効くか」も大切です。型が正しくても、呼び出し時に毎回明示的なジェネリクス指定が必要だったり、エラーメッセージが読みにくかったりすると、利用者の体験は悪くなります。型安全性と利用しやすさは両立させる必要があります。

### 5-5. モノレポとサブパス exports の考え方

実務では、TypeScript を単体のアプリケーションだけでなく、モノレポや複数パッケージ構成で使うことがよくあります。そうなると、ファイル単位の `import` / `export` だけでなく、「パッケージとして何を見せるか」が問題になります。

サブパス exports は、その公開面を制御するための重要な仕組みです。たとえば `@acme/utils/date` や `@acme/ui/button` のように、利用者が辿ってよい入口を意図的に設計できます。

これがない状態で深い相対パス import が広がると、利用者が内部構造へ直接依存し始めます。すると、ディレクトリ構成を変えただけで破壊的変更になってしまいます。

モノレポでは特に、次の点を意識すると安定しやすくなります。

- パッケージごとの責務をはっきり分ける
- 入口を `exports` で制御する
- 型定義も公開契約として扱う
- project references や build 境界と API 境界を混同しない

`TaskHub` のモノレポ構成をざっくり書くと、次のようなイメージになります。

```text
packages/
  shared/
  api-client/
apps/
  cli/
  web/
```

このとき `shared` には内部モデルや共通ユーティリティを置き、`api-client` には外部 API 境界と変換処理を閉じ込め、`cli` と `web` はそれぞれ必要な公開面だけを使う、という分割にすると責務が見えやすくなります。構造全体をまとめて見たいときは、付録 A が 5章の補助になります。

モノレポでありがちなのは、「同じリポジトリにあるから自由に参照してよい」と考えることです。しかし、物理的に近いことと、設計上近いことは別です。近すぎる import は、短期的には便利でも、長期的にはコードベースを硬直させます。

この章のテーマは、型をうまく書くことではなく、型を含む公開面をどう制御するかでした。次章では、こうした設計を Node.js の実行環境へどう落とし込むかを見ていきます。
