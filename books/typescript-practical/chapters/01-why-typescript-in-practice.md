# 1. TypeScript を実務で使う意味

## この章で伝えること

- TypeScript を導入する価値を、補完や型エラーの検出だけでなく設計の観点から説明する
- 本書全体で扱う「境界」「制約」「運用」という軸をここで定義する

## 節構成

### 1-1. JavaScript の柔軟さが事故になる瞬間

JavaScript の強みは、少ない前提で素早く動くものを作れることです。小さなスクリプト、画面のちょっとした振る舞い、社内ツールのプロトタイプなどでは、その柔軟さが大きな武器になります。一方で、その柔軟さはコードベースが長く生きるほど、少しずつ別の顔を見せるようになります。

たとえば、最初は文字列だと思っていた値が、ある API からは `null` で返るかもしれません。内部だけで使う想定だったオブジェクトが、別のモジュールからも参照されるようになるかもしれません。画面では必ず存在する前提で書いた値が、SSR や非同期読み込みの導入で「まだない」状態を持つかもしれません。

厄介なのは、JavaScript が悪いというより、変化に対して暗黙の前提が増えやすいことです。実務のコードでは、仕様変更、担当者交代、依存ライブラリ更新、入力元の追加が起き続けます。最初は正しかった前提が、半年後には静かに崩れていることも珍しくありません。

次のようなコードは、書いた直後には何の違和感もありません。

```ts
function formatPrice(price) {
  return price.toFixed(2);
}
```

この関数は「`price` には数値が入る」という暗黙の前提に依存しています。ところが実務では、フォーム入力、JSON、環境変数、DB からの値など、外から来るデータは簡単にその前提を破ります。`"100"`、`null`、`undefined`、あるいは `{ amount: 100 }` のような値が混ざった瞬間に、この関数は壊れます。

問題は、壊れることそのものより、「どこで何を前提に壊れるのか」がコードから読みにくいことです。JavaScript の柔軟さは、前提が小さいうちは速さになりますが、前提が増えると読みにくさに変わります。

### 1-2. TypeScript が解決する問題、解決しない問題

TypeScript は、この「暗黙の前提」をコード上に引き上げるための道具です。値の形、関数の入出力、`null` がありうるかどうか、モジュールが何を公開しているか、といった情報を、コメントではなく型として表現できます。

先ほどの例を TypeScript で書き直すと、少なくとも前提は明示されます。

```ts
function formatPrice(price: number): string {
  return price.toFixed(2);
}
```

この時点で、呼び出し側が文字列や `null` を渡したときに、静的検査の段階で気づけるようになります。さらに、関数の契約が短いシグネチャとして見えるため、読み手も「この関数が何を期待しているか」を把握しやすくなります。

ただし、TypeScript にもできないことがあります。代表的なのは、ランタイムで入ってくる値の正しさを保証することです。`fetch()` で受け取った JSON、ユーザー入力、環境変数は、型注釈を書いただけでは安全になりません。`price: number` と書いても、実際に `"100"` が飛んでくることはあります。

つまり、TypeScript が解決するのは「コードの内側で共有される前提の見える化」と「変更時に崩れる箇所の早期発見」です。一方で、「外部入力の信頼性」「設計そのものの良し悪し」「読みやすい責務分割」は、TypeScript だけでは解決しません。

この区別はとても重要です。TypeScript を導入したチームが期待外れを感じるのは、TypeScript を万能な安全装置として扱ったときです。逆に、どこまでを TypeScript に任せ、どこからを設計やランタイム検証で支えるかを分けて考えられると、TypeScript は非常に強い道具になります。

### 1-3. 「型を書く」のではなく「境界を設計する」

TypeScript の学習が途中で苦しくなる理由のひとつは、「型を書くこと」自体が目的になってしまうからです。複雑な条件型を書けること、型パズルを解けること、見た目に高度なジェネリクスを使えることは、それ自体では実務価値を保証しません。

実務で本当に大事なのは、どこに境界があるかを意識することです。たとえば次のような境界があります。

- API レスポンスとアプリケーション内部
- フォーム入力とドメインロジック
- UI コンポーネントとデータ取得層
- ライブラリの内部実装と公開 API
- 環境変数とアプリケーション設定

境界では、値の形が変わります。責務も変わります。信頼できるかどうかも変わります。TypeScript の型は、その変化を曖昧にしないためにあります。

たとえば、外部 API のレスポンス型をそのまま画面コンポーネントへ流すと、「外部仕様の揺れ」が UI 全体へ伝播します。逆に、境界で一度パースし、自分たちのアプリケーションにとって都合のよい型へ変換しておけば、壊れやすい面を局所化できます。

```ts
type ApiUser = {
  id: string;
  display_name: string | null;
  created_at: string;
};

type User = {
  id: string;
  displayName: string;
  createdAt: Date;
};
```

この例で重要なのは、`ApiUser` と `User` の違いです。前者は外部との境界で受け取る値、後者は内部で使いやすい形です。TypeScript をうまく使うとは、この境界を曖昧にしないことです。

本書では、型を「正しさの記号」ではなく、「境界と責務を切り分ける道具」として扱います。どの章でも、型の細かな書き方より、どこで型を効かせると設計事故が減るのかを重視します。

### 1-4. 本書で扱う前提と対象範囲

本書は、JavaScript をまったく知らない読者のための入門書ではありません。変数宣言、関数、配列、オブジェクト、モジュールといった基本構文は、すでに一通り触れたことがある前提で進めます。その代わり、「型は書いているが設計に活きていない」「Node.js とフロントエンドで書き方がばらつく」「設定やビルドの理由が分からない」といった実務上の悩みに答えることを目指します。

また、本書は特定フレームワークの本ではありません。React、Next.js、NestJS などの固有機能は必要に応じて触れますが、主役はあくまで TypeScript そのものと、その周辺で必要になる判断軸です。フレームワークをまたいで使える原則を優先します。

一方で、本書だけで扱いきらないものもあります。たとえば、Git の履歴設計やレビュー運用の詳細は本シリーズの `Git & GitHub` 巻が担当します。依存関係管理やテスト一般の考え方も、必要に応じて共通説明へ寄せます。本書は、そのうえで「TypeScript では何が固有に難しいのか」を明確にする立場を取ります。

本書は、まず 2章から4章で型と境界の原則を固め、次に 5章から7章でそれをモジュール設計、Node.js、フロントエンドへ落とし込みます。8章から10章ではツールチェーン、`tsconfig`、2026年時点の移行論点を整理し、11章で継続運用の原則へまとめます。

最初に覚えておいてほしいのは、TypeScript は「厳密な型を書く言語」ではなく、「変化に耐える設計を助ける言語」だということです。この視点があると、細かな文法や設定の意味がぐっとつながりやすくなります。

### 1-5. 通しサンプル `TaskHub` の紹介

本書では、章ごとの概念が空中戦にならないように、`TaskHub` という小さな通しサンプルを扱います。`TaskHub` は、タスクを取得・表示・更新するシンプルなアプリケーション群です。ひとつの大きなアプリではなく、役割ごとに次の 4 つへ分かれています。

- `shared`: 共通型とユーティリティを置くパッケージ
- `api-client`: 外部 API を呼び、レスポンスを内部モデルへ変換する層
- `cli`: タスクを一覧・同期する Node.js CLI
- `web`: タスクを表示・編集するフロントエンド

この構成を選んだのは、TypeScript の実務で本当に難しいのが、単一ファイルの型の書き方ではなく、「複数の境界をまたぐときに何を共有し、何を変換するか」だからです。`TaskHub` では、同じドメインを Node.js とフロントエンドの両方から触るため、型を共有すべき場所と、共有してはいけない場所の違いを追いやすくなります。

各章ではこのサンプルを少しずつ改善します。2章では型の基本方針を確認し、4章では外部 API レスポンスをそのまま使わない形へ直し、5章では package 境界を見直し、6章と7章では CLI と UI の設計へ展開します。本書の概念は、すべて `TaskHub` の改善として具体化されます。

`TaskHub` の全体像を途中で見返したくなったら付録 A を、型と関数の対応を追い直したい場合は付録 B を参照してください。
