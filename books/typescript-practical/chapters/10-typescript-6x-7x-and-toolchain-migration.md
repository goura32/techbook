# 10. TypeScript 6.x / 7.x とツールチェーン移行

## この章で伝えること

- 2026 年時点の大きな変化を、機能紹介ではなく移行判断として整理する

## この章の前提

- 本章のバージョン状況は 2026年5月12日時点の公式情報に基づく
- 本文では、移行判断に効く転換点だけを日付付きで扱う
- 細かな前後関係や参考バージョンは章末の公式情報一覧へまとめる

## 節構成

### 10-1. TypeScript 5.9 から 6.x への変化

TypeScript の更新を追うとき、つい新機能一覧に目が向きがちです。しかし実務で本当に重要なのは、「新しい文法が足されたか」よりも、「既存コードベースの前提がどこで変わるか」です。この章では、5.9 から 6.x への流れを、単発の便利機能よりも将来のツールチェーン移行の地ならしとして見ていきます。

5.9 系までは、多くのプロジェクトにとって「いまの TypeScript の延長」として理解しやすい世界でした。`tsc` を中心に、`tsserver`、IDE 補完、Lint、テスト、bundler 連携が組み合わさる構図は大きく変わっていません。一方で、2026年3月23日に公開された TypeScript 6.0 以降は、その延長上にありつつも、7.0 の native toolchain を意識した判断が必要になります。

ここで大切なのは、6.x を「移行前提の時代」として見ることです。つまり、

- いまの設定が将来の移行を阻害しないか
- 暗黙の前提に依存しすぎていないか
- 型エラーやモジュール解決の揺れをどこまで許容しているか

といった視点が必要になります。

実務上は、5.9 系で安定しているからすぐに 6.x へ飛びつく、あるいは逆に 6.x は新しいから全部避ける、という二択ではありません。重要なのは、自分たちのプロジェクトで何がボトルネックなのかを見たうえで、更新の意味を判断することです。

### 10-2. 7.0 native preview は何を変えるのか

7.0 native preview が注目されている理由は、単なるバージョン番号の更新ではありません。TypeScript の開発体験において、長年前提だった JavaScript 実装の `tsc` / `tsserver` とは異なる方向が示されているからです。ここでは、これを「すぐ全面移行すべき完成品」というより、「今後の主戦場がどこへ向かうかを示すサイン」と考えるのが適切です。

公式情報ベースで整理すると、いま押さえるべき状況は次の通りです。

- `5.9`: 安定版として広く使える基準点
- `6.0`: 2026年3月23日に安定版リリース済みで、7.0 への橋渡し役
- `7.0 Beta`: 2026年4月21日にベータ公開。Go ベースの新基盤を前提にした次世代ライン
- `native preview`: 7.0 系へ向かう導線として理解しておくべき周辺動向

開発者にとって分かりやすい変化は、まず速度です。大規模プロジェクトでは型チェックやエディタ応答の遅さが日常的なストレスになります。native toolchain が注目される背景には、その遅さを構造的に改善したいという文脈があります。

ただし、変わるのは速さだけではありません。周辺ツールとの接続のしかた、エディタ統合、既存プラグインとの相性、CI での実行方法、デバッグ時の期待値も見直しが必要になります。つまり 7.0 native preview は、「TypeScript そのもの」だけでなく、「TypeScript をどう運用するか」の前提を揺らします。

ここで冷静に見ておきたいのは、preview は preview、beta は beta だということです。未来の方向性を見る材料としては重要ですが、安定運用中の商用プロジェクトにそのまま全面適用するかは別問題です。実務では、次の 2 つを分けて考える必要があります。

- 何が将来の標準になりそうか
- いま採用してもよいほど安定しているか

この区別がないと、技術的な関心とプロジェクト上の判断が混ざってしまいます。

### 10-3. 互換性リスクをどう見るか

TypeScript の更新は、文法エラーが出るかどうかだけで判断できません。実際には、モジュール解決、型推論、標準ライブラリ型、ビルド手順、エディタ挙動など、複数のレイヤで影響が出ます。つまり互換性リスクとは、「コンパイルが通るか」より広い概念です。

実務で見落としやすいリスクには、次のようなものがあります。

- `tsconfig` の解釈差
- ESM/CJS 周辺の挙動差
- 補助ツールが参照する TypeScript バージョン差
- 型エラーの厳しさ変化
- エディタと CI で診断結果がずれること

とくに怖いのは、「ローカルでは問題ないのに、CI か別の開発者環境でだけ落ちる」状態です。TypeScript はツールチェーンの中心にいるため、周辺ツールの更新タイミングが少しずれるだけでも不整合が起こります。

互換性リスクを見るときは、更新内容を読むだけでなく、プロジェクト側の依存関係も確認する必要があります。たとえば、

- ESLint プラグインは追従しているか
- bundler や test runner は想定している TypeScript バージョンをサポートしているか
- 社内ライブラリの型定義は新しい前提に耐えられるか

といった確認が必要です。

つまり、TypeScript の更新判断は言語更新の判断であると同時に、開発基盤更新の判断でもあります。

### 10-4. 既存プロジェクトの移行計画

既存プロジェクトの移行で重要なのは、「正しい最終状態」をいきなり目指さないことです。多くのプロジェクトでは、TypeScript 本体だけでなく、Node.js バージョン、bundler、Lint、テストランナー、社内テンプレート、CI イメージが絡みます。そのため、更新を一枚岩として扱うと失敗しやすくなります。

移行計画では、まず影響範囲を分けるのが有効です。たとえば次のように分けて考えられます。

1. 型検査だけを先に更新する
2. エディタやローカルツールの更新を追う
3. CI の更新を追う
4. ビルドや配布系の更新を追う

こうしておくと、どこで問題が起きたかを切り分けやすくなります。また、更新前後で比較するための基準も必要です。

- 型エラー数は増えたか
- ビルド時間はどう変わったか
- エディタ応答は改善したか
- 開発者の詰まりどころは変わったか

加えて、移行には「戻せること」も大切です。特に preview や beta を試す場合は、ロールバックの手順が曖昧だと、本番ではなくてもチーム全体の開発が止まります。実験と採用を分けて考え、検証用ブランチや限定パッケージ、サンドボックス環境を使うほうが安全です。

移行は技術イベントではなく、変更管理です。だからこそ、速さや新しさだけでなく、段階性と可逆性を持たせる必要があります。

### 10-5. 速さと安定性のどちらを優先するか

最終的に移行判断でぶつかるのは、速さと安定性のトレードオフです。開発体験を改善したい気持ちは強い一方で、商用コードベースでは「速くなったが周辺ツールが不安定になった」状態は歓迎しづらいことがあります。

ここで大切なのは、一般論ではなく、自分たちにとってのコストを測ることです。たとえば、

- 1 日に何回型チェック待ちが発生するか
- 補完の遅さがどれくらい生産性を落としているか
- 更新による不具合対応へどれくらい時間を割けるか
- チームにツールチェーンを調整できる人がいるか

といった観点で見ると、判断は変わります。

小規模なプロジェクトや個人開発では、新しいツールチェーンを早めに試す価値が高いことがあります。逆に、多人数が関わるプロダクトや長寿命の社内基盤では、ひとつの更新が広い影響を持つため、安定性を優先したほうが合理的なこともあります。

重要なのは、「先進性」と「保守性」を対立させないことです。たとえば、新規プロジェクトで先に試し、既存プロジェクトへの展開は後で考える、という形なら両立しやすくなります。

この章で扱った 6.x / 7.x の話は、単なる最新版紹介ではありません。TypeScript を長く使うチームが、どのように変化と付き合うかの話です。次の最終章では、その視点をより広くして、継続運用で壊れない TypeScript の原則をまとめます。
