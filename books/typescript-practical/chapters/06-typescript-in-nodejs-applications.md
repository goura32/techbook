# 6. Node.js アプリケーションでの実践

## この章で伝えること

- TypeScript を Node.js の現場でどう無理なく使うかを整理する

## 節構成

### 6-1. CLI、スクリプト、サーバーの違い

Node.js で TypeScript を使うといっても、対象はひとつではありません。短いワンショットスクリプト、CLI ツール、長時間動く API サーバー、バッチ処理、ワーカー、ビルドツールなど、それぞれ求められる性質が違います。ここを区別せずに「Node.js の書き方」としてひとまとめにすると、設計判断がぼやけます。

たとえば、CLI ツールでは次のような点が重要になります。

- 引数と標準入出力の扱い
- 終了コード
- 失敗時のメッセージ
- 実行速度

一方でサーバーでは、次の観点が前に出ます。

- リクエストごとの境界
- ログと監視
- エラーの伝播
- 設定とライフサイクル管理

スクリプトはさらに別です。短く書けることが大事な場面もありますが、何度も使うなら設定の読み込み、エラー出力、入力の検証が必要になります。最初は雑に見えてよいスクリプトも、繰り返し使うなら徐々に「小さなアプリケーション」として扱う必要が出てきます。

TypeScript がここで役立つのは、形の違うプログラムに対して共通の設計原則を持ち込めることです。CLI でもサーバーでも、外部入力の検証、設定の境界、失敗の表現、公開 API の絞り込みといった考え方は共通しています。

本書の通しサンプル `TaskHub` では、この章の対象は `cli` と `api-client` です。4章で整理した境界原則を、Node.js の実行環境にどう載せるかを見る章として読むとつながりやすくなります。

`TaskHub` の CLI は、たとえば `taskhub sync --project acme` のような形で動くことを想定します。ここでは「引数を受け取って API を呼び、内部モデルへ変換し、標準出力へ整形して返す」までがひとつの流れになります。TypeScript の価値は、その一連の境界を別々に整理できることです。流れ全体を一覧で確認したい場合は、付録 B を併せて読むと追いやすくなります。

### 6-2. ESM/CJS と実行環境の整理

Node.js で TypeScript を扱うとき、多くの人が最初に混乱するのが ESM と CommonJS です。ここでは仕様の歴史を細かく追うより、「自分のプロジェクトがどの前提で動いているか」を明確にすることが重要です。

少なくとも次の 3 つは区別して考える必要があります。

- TypeScript がどのモジュール構文を出力するか
- Node.js がその出力をどう解釈するか
- 実行時ツールや bundler が何を期待するか

たとえば `tsconfig` の `module` が `NodeNext` でも、`package.json` の `type`、実行コマンド、出力先の拡張子、依存パッケージの形式によって挙動は変わります。ここを「とりあえず動いた」で済ませると、後でテスト環境や CI、ライブラリ配布で必ず詰まります。

実務では、まずどちらを基準にするかを決めるのが大切です。2026年時点で新規プロジェクトなら、Node.js 側は ESM を基準に考えるほうが素直です。本書でも、`package.json` の `"type": "module"` と `tsconfig` の `module: "nodenext"` を主例として扱います。一方で、既存資産や依存ライブラリの事情で CJS を維持したほうが安全なケースもあります。大事なのは流行に乗ることではなく、チームで前提をそろえることです。

さらに、開発時の実行方法も含めて整理が必要です。`tsx`、`ts-node`、ビルド後に `node dist/...` を実行する方式、テストランナー内で直接解釈する方式では、トラブルの種類が違います。TypeScript 本体の設定だけを見ても足りず、「どう実行するか」まで含めてツールチェーンとして考える必要があります。とくに ESM 基準では、`.js` 出力を `package.json` と整合させること、拡張子と import 解決を曖昧にしないことが重要です。

本書の立場を先に言うと、Node.js 側の説明は次の前提で読むとつながりやすくなります。

- 新規の Node.js コードは ESM 基準で考える
- `package.json` では `"type": "module"` を明示する
- TypeScript では `module: "nodenext"` を主例にする
- CJS は移行や互換性の論点として短く扱う

### 6-3. 設定、ログ、終了コードの扱い

Node.js アプリケーションを実務で使うなら、ロジック以前に整えておきたいのが設定、ログ、終了コードです。これらは機能要件ではないため後回しにされがちですが、放置すると運用をいちばん苦しくする部分でもあります。

設定については、4章で見たとおり、生の `process.env` をアプリケーション全体で触らないことが基本です。起動時に一度読み込み、検証し、内部で使う設定型へ落とし込むほうが安全です。

ログも同じです。`console.log()` をあちこちで使うこと自体が悪いわけではありませんが、運用コードでは少なくとも「どのレベルのログか」「構造化されているか」「どこで集約されるか」を意識したほうがよいです。型の観点でも、ログのコンテキスト情報をオブジェクトとしてそろえておくと、呼び出し側のばらつきを抑えやすくなります。

終了コードは、CLI やバッチ処理では特に重要です。失敗したのに常に `0` で終わるプログラムは、自動化や監視と相性が悪くなります。TypeScript の本だからといって省略したくなる部分ですが、実務という軸で見るとここは避けて通れません。

たとえば CLI ツールでは、次のような方針を最初に決めておくとよいです。

- 入力エラーは利用者向けの短いメッセージで返す
- 想定外エラーはログを残して非 0 で終了する
- 機械向け出力と人間向け出力を混ぜない

これらは TypeScript 固有の文法ではありませんが、型で設定やログコンテキストを整えることで、アプリケーション全体の一貫性を保ちやすくなります。

ESM 基準で進める場合でも、この章で主に見たいのは import 構文そのものではありません。設定、境界、失敗の扱いを `ESM として素直に動く Node.js アプリケーション` へどう載せるかです。

`TaskHub` の CLI 用設定を少し具体化すると、次のようになります。

```ts
type TaskHubConfig = {
  apiBaseUrl: string;
  apiToken: string;
  defaultProject: string | null;
};

function loadTaskHubConfig(env: NodeJS.ProcessEnv): TaskHubConfig {
  const apiBaseUrl = env.TASKHUB_API_BASE_URL;
  const apiToken = env.TASKHUB_API_TOKEN;

  if (!apiBaseUrl) {
    throw new Error("TASKHUB_API_BASE_URL is required");
  }

  if (!apiToken) {
    throw new Error("TASKHUB_API_TOKEN is required");
  }

  return {
    apiBaseUrl,
    apiToken,
    defaultProject: env.TASKHUB_DEFAULT_PROJECT ?? null,
  };
}
```

ここで重要なのは、CLI のどこからでも `process.env` を読むのではなく、起動時に `TaskHubConfig` を確定させることです。そうしておくと、残りの処理は「設定済みのアプリケーション」として書けます。

### 6-4. 外部 API 呼び出しと型安全

Node.js アプリケーションでは、外部 API 呼び出しがごく自然に登場します。ここでの典型的な失敗は、「SDK やレスポンス型があるから安全だろう」と考えてしまうことです。実際には、ネットワークエラー、タイムアウト、ステータスコード、部分的なレスポンス破損、API バージョン差分など、型だけでは吸収できない問題が多くあります。

重要なのは、呼び出しコードを次の 3 層に分けて考えることです。

- リクエストを送る
- レスポンスを検証・変換する
- アプリケーション用の結果として返す

```ts
type PaymentStatus = "pending" | "paid" | "failed";

type Payment = {
  id: string;
  status: PaymentStatus;
};

async function getPayment(paymentId: string): Promise<Payment> {
  const response = await fetch(`https://api.example.com/payments/${paymentId}`);

  if (!response.ok) {
    throw new Error(`request failed: ${response.status}`);
  }

  const json = await response.json();

  // 実際にはここで検証と変換を行う
  return {
    id: String(json.id),
    status: json.status as PaymentStatus,
  };
}
```

この例では最後の `as PaymentStatus` が気になります。こうしたアサーションは、小さく局所化されていれば実用的ですが、広がるとすぐに危険な地帯になります。理想は、境界でしっかり検証してから、内部ではアサーションをできるだけ減らすことです。

`TaskHub` の場合は、4章で作った `toTask()` をここで使います。

```ts
async function fetchTasks(config: TaskHubConfig): Promise<Task[]> {
  const response = await fetch(`${config.apiBaseUrl}/tasks`, {
    headers: {
      Authorization: `Bearer ${config.apiToken}`,
    },
  });

  if (!response.ok) {
    throw new Error(`TaskHub request failed: ${response.status}`);
  }

  const json = (await response.json()) as TaskApiResponse[];
  return json.map(toTask);
}
```

実際には `as TaskApiResponse[]` の手前でもう一段検証を入れたいところです。ただ、構造として大事なのは、`fetchTasks()` が `Task[]` を返すところまで責任を持つことです。CLI 本体は、外部仕様ではなく内部モデルを扱うようになります。

さらに実務では、リトライ、バックオフ、タイムアウト、認証更新、監査ログなども考慮が必要です。本書では外部 API の詳細実装本にはしませんが、「型があるだけでは運用に耐えない」という視点は強く持っておきます。

なお、既存の社内 CLI や古い依存関係では、CJS を維持したほうが安全なこともあります。その場合でも、「設定の入口を固定する」「境界で検証する」「内部モデルを返す」というこの章の原則は変わりません。変わるのは import/export と実行時の前提だけです。

### 6-5. バックエンドのエラー設計

Node.js のバックエンドで TypeScript を使うとき、エラー設計は型設計と密接につながります。問題は、例外を使うかどうかではありません。どの層でどんな失敗が起こりうるかを、読み手が追えるかどうかです。

ありがちな失敗は、どんな問題も全部 `throw new Error(...)` で済ませてしまうことです。これは小さなコードでは十分でも、処理が増えると「どのエラーが利用者向けで、どのエラーが内部障害なのか」が分からなくなります。

実務では、少なくとも次の区別を持っておくと整理しやすくなります。

- 入力不正
- 業務上の失敗
- 外部依存の失敗
- 想定外の内部障害

これらをすべて別クラスにする必要はありませんが、同じ扱いにしないことは重要です。たとえば入力不正は 400 系として返せても、外部依存の失敗は 502 や 503 に寄せたいかもしれません。業務上の失敗は 409 や 422 のように扱うこともあります。

TypeScript の型は、エラーの分類を呼び出し側へ伝える助けになります。`Result` 型を使う場合もあれば、アプリケーション内部では例外、境界ではレスポンス変換という設計もあります。大切なのは、「どこで握りつぶさず、どこで利用者向けに変換するか」を決めておくことです。

Node.js で TypeScript を使う価値は、言語機能そのものだけではありません。設定、外部 API、エラー、実行環境のような実務上の境界を、型と設計の両方で整えられることにあります。次章では、その考え方をフロントエンド側へ移していきます。
