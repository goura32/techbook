# 3章 ブランチ戦略と日常運用

ブランチ戦略は、宗教ではありません。trunk-based が常に正しいわけでも、release branch が古いわけでもありません。大切なのは、チームのサイズ、レビュー速度、CI の重さ、リリースの切り方に対して、どの戦略が一番破綻しにくいかを選ぶことです。

trunk-based は、小さな変更を頻繁に main へ流せるチームに向いています。変更が小さければ競合は減り、レビューも軽くなります。その代わり、CI とレビューが詰まると全体が止まりやすくなります。release branch は、リリース準備や検証期間を切り分けたいときに有効ですが、分岐後の差分管理が増えます。長寿命ブランチは段階管理をしやすい一方で、履歴の乖離と競合が増えやすくなります。

`BeaconBoard` のような小規模プロダクトでは、基本は短命の feature branch を切り、レビュー後すぐに main へ戻す運用が扱いやすいです。重要なのは、ブランチを切ることそのものではなく、いつ main へ追従し、いつ差分を整理し、いつマージするかです。feature branch を長く生かしすぎると、それだけで競合とレビュー負荷が増えます。

日常運用では、ローカル作業を汚しすぎないことも大切です。作業ブランチの役割を曖昧にして、思いつきの修正を次々積み重ねると、後でコミット整理が難しくなります。逆に、目的ごとに branch を分け、不要な実験は早めに捨てるほうが、履歴がきれいに保てます。

main への追従方法もチームで揃えておいたほうがよい点です。共有前の feature branch なら `rebase` で履歴を整える選択肢は自然です。一方で、公開済みの branch や他の人が触っている履歴では、安易な書き換えは混乱を招きます。ブランチ戦略の議論は、どのコマンドを使うかより、どの範囲まで書き換えを許すかとセットで考える必要があります。

この章の要点は、ブランチ戦略を抽象論で終わらせないことです。レビューの速さ、CI の重さ、リリース頻度、チーム規模を見て、変更をどれだけ小さく main に戻せるかで考えると、過剰に複雑な運用を避けやすくなります。次の章では、その変更を Pull Request とレビューの単位としてどう扱うかを見ていきます。
