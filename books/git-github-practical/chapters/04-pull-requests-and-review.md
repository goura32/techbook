# 4章 Pull Request とレビューの進め方

Pull Request は、マージ前の通過点ではありません。チームで変更をレビューし、意図を共有し、運用上の安全を確かめるための単位です。だからこそ、PR の質はコードそのものだけでなく、変更の切り方や説明文の書き方にも大きく左右されます。

まず大切なのは、PR をレビュー単位として設計することです。コミット単位が良くても、PR に無関係な変更が混ざると、レビューは重くなります。逆に、PR が小さく、背景が明確で、何を見てほしいかが書かれていると、レビューはかなり進めやすくなります。`BeaconBoard` でも、機能追加の PR と、保護設定の更新 PR とでは見るべき観点が違います。その違いが本文やテンプレートから分かることが重要です。

レビューコメントも、指摘の正しさだけでは不十分です。なぜ気になるのか、どのリスクを見ているのか、必須なのか改善案なのかが分かる書き方のほうが、チームの合意形成を助けます。レビューは議論の場でもありますが、議論のためだけに止める場ではありません。責務が曖昧なコメントは、PR を長く停滞させやすくなります。

承認と責任分担も明確にしたい点です。承認は「全部完璧である」の意味ではなく、「この変更をこの形で入れてよい」と判断した印です。そのため、どの観点を誰が見るのかをチームである程度そろえておくと、レビュー漏れが減ります。コードオーナー、ドメイン担当、CI の責務分担は、人数が増えるほど重要になります。

レビューを止める大きな要因のひとつは、変更が大きすぎることです。もうひとつは、差分の背景が読めないことです。Pull Request の本文に、背景、変更点、影響範囲、確認してほしい点が短く揃っているだけでも、レビュー体験はかなり変わります。テンプレートの価値はここにあります。

この章の要点は、Pull Request を「レビューしてもらうための箱」としてではなく、「変更の意図と責務を共有する単位」として見ることです。付録 B の対応表や付録 C の運用断片を行き来しながら読むと、日常の branch 運用と PR のつながりが見えやすくなります。次の章では、レビュー前後で特に詰まりやすい競合解消、rebase、cherry-pick の実務へ進みます。
