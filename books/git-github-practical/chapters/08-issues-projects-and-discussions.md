# 8章 Issue、Projects、Discussions の使い分け

変更管理は、コード差分だけで完結しません。なぜその変更を行うのか、どの作業がどのリリースに入るのか、仕様の相談をどこで行うのか。こうした情報がコード外に散らばると、後から見返したときに履歴がつながりにくくなります。

Issue は、作業単位と判断の記録に向いています。修正、改善、調査、負債返済。こうしたものを `何をするか` `なぜ必要か` `完了条件は何か` まで含めて残しておくと、Pull Request の背景説明も短くできます。Issue が雑談の場になりすぎると追いにくくなりますが、逆に一切残さないと変更の意図が履歴へつながりません。

Projects は、複数の Issue や PR の流れを見るのに向いています。何が着手中で、何がレビュー中で、何が止まっているかを、チームで共有しやすくなります。ただし、Projects に情報を寄せすぎて、Issue や PR 本文が薄くなると本末転倒です。作業の流れを見るのが Projects、作業の中身を残すのが Issue と考えると整理しやすくなります。

Discussions は、仕様相談や比較的長めの会話に向いています。ただし、Pull Request の代わりにはなりません。レビュー対象のコード変更についての合意は、最終的には PR や Issue に戻ってこないと、履歴として追いにくくなります。Discussions は入口や相談の場には便利ですが、実装判断の最終記録をそこだけに閉じ込めないことが大切です。

この章で大事なのは、GitHub の機能を全部使うことではありません。コード外の判断を、どこにどう残すと後で追いやすいかを考えることです。Issue、Projects、Discussions は、その役割を分けて使うと強くなります。次の章では、こうして流してきた変更を、タグ、リリース、バージョニングへどうつなぐかを見ます。
