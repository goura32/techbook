# 2章 コミット、履歴、差分の基本設計

良い Git 運用の出発点は、良いコミットです。ここでいう良いコミットとは、すごいテクニックが詰まったコミットではありません。`何を変えたのか` と `なぜ変えたのか` が追いやすく、レビューしやすく、後で戻しやすいコミットです。実務では、履歴の読みやすさはコード品質の一部だと考えたほうがよいです。

まず意識したいのは、変更単位を小さく切ることです。ひとつのコミットにリファクタリング、機能追加、テスト修正、ドキュメント更新が全部入ると、レビューする側はどこに注意を向けるべきか分からなくなります。逆に、機能追加の前に名前変更だけを切り出す、テスト追加を独立させる、設定変更を別コミットにする、といった工夫をすると、差分の意味が見えやすくなります。

コミットメッセージも、履歴の一部です。短い 1 行で要点を示し、必要なら本文で背景を補うだけでも、後から履歴を追う負荷はかなり下がります。大事なのは「何をしたか」だけでなく、「なぜ必要だったか」を残すことです。特に復旧時や `cherry-pick` を考える場面では、コミットメッセージの質が効きます。

差分の読みやすさは、コードの量だけで決まりません。並び順、機械的変更と意味のある変更の混在、ファイルのまたぎ方、不要なフォーマット差分の有無なども大きく影響します。`BeaconBoard` でも、たとえば API 名称変更と docs 更新を同時に行う場面はありますが、それを 1 コミットにするか、2 コミットに分けるかでレビュー体験が変わります。

実務では、「動くから 1 コミットでよい」という判断が積み重なると、レビューも復旧も苦しくなります。逆に、コミットを細かくしすぎて意味が見えなくなることもあります。大切なのは、コミット 1 つが 1 つの理由を持っていることです。レビューする人がその理由を追えるなら、そのコミットはかなり良い方向にあります。

履歴設計は後からでも改善できますが、共有された履歴に入る前のほうがはるかに安く整えられます。だからこそ、きれいにする努力は PR を出す前に行う価値があります。次の章では、そうして作った変更を、ブランチ戦略と日常運用の中へどう載せるかを見ていきます。
