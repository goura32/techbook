# 1章 Git と GitHub をどう使い分けるか

Git と GitHub は、しばしばひとつのものとして扱われます。しかし実務では、この 2 つを分けて考えたほうが理解しやすくなります。Git は履歴管理の仕組みです。コミットを作り、ブランチを切り、差分を持ち、履歴をたどるための道具です。GitHub は、その履歴をチームで共有し、Pull Request、レビュー、保護設定、CI、リリースといった運用を乗せる場です。

この区別が曖昧だと、問題が起きたときに「どこで直すべきか」が見えにくくなります。たとえば、コミットが大きすぎてレビューしづらい問題は、まず Git 側の変更単位の問題です。一方で、main に危険な変更が直接入ってしまう問題は、GitHub 側の rulesets やレビュー運用の問題です。同じ「変更管理」の話でも、責務の場所が違います。

個人開発では、この違いがあまり表面化しないことがあります。自分しか触らないなら、多少雑な履歴でも困らないかもしれませんし、レビューも不要です。しかしチーム開発では、変更は自分のためだけではなく、読む人、レビューする人、リリースする人、障害対応する人のためにも残ります。そこで初めて、履歴の読みやすさ、レビュー単位、保護設定、復旧可能性が効いてきます。

本書で扱う `BeaconBoard` も、まさにその前提で考えます。Web アプリ、API、docs を持つ小さなプロダクトですが、main は共有資産であり、レビューと CI を通して変更を流します。ここで重要なのは、Git の操作を上達させることそのものではありません。変更を安全に流せるよう、どこで止め、どこで確認し、どこで戻せるようにするかを考えることです。

そのために本書で繰り返す視点は、`変更を小さく保ち、意図を明確にし、復旧可能な形で流す` ことです。Git は何でもできるため、ついその場の最短操作に流れがちです。しかしチーム運用で本当に強いのは、最短ではなく、後から読めて戻せる運用です。ローカルでは自由でも、共有ブランチでは慎重であるべき場面があります。履歴をきれいにする価値も、まずは共有前の段階で大きくなります。

この章では、Git と GitHub の役割分担を見取り図として示しました。次の章からは、良いコミットとは何か、レビューしやすい差分とは何か、ブランチをどう伸ばすか、保護設定をどう置くか、壊したときにどう戻すかを順に見ていきます。`BeaconBoard` の全体構成を先に見返したいときは付録 A が役に立ちます。
