# 11章 チームに定着させる運用ルール

Git と GitHub の運用は、一度決めたら終わりではありません。チームが変わり、プロダクトが変わり、CI が重くなり、レビュー量が増えると、以前はうまくいっていたルールが合わなくなることがあります。だからこそ、本当に必要なのは「強いルール」より、「小さく改善し続けられる運用」です。

まず大切なのは、ルールを増やしすぎないことです。コミットメッセージの形式、PR テンプレート、必須レビュー数、必須チェック、branch 命名規則、release 手順。これらを全部厳密に固めると、守ること自体が目的化しやすくなります。最初に固定したいのは、履歴を壊さないこと、変更単位を小さくすること、main を守ること、事故時に戻せることです。

テンプレートと自動化は、その土台を支えるのに向いています。PR テンプレート、Issue テンプレート、rulesets、CI、merge queue。これらは人の善意に頼りすぎないための道具です。ただし、自動化すればすべて解決するわけではありません。例外運用や緊急対応は必ず発生するので、そこをどう記録し、どう通常運用へ戻すかもセットで考える必要があります。

例外を放置しないことも重要です。急ぎだから直 push した、CI が不安定だから必須チェックを外した、レビューが間に合わないから bypass した。こうした判断は実務では起こり得ます。しかし、それを一時対応で終わらせず、後から見直してルールへ戻すことができるかどうかが、チームの強さを分けます。

最終的に一番効くのは、共通理解です。何が良いコミットか、どこで rebase を使ってよいか、main を壊したら何を最初に見るか、rulesets は何を守るためにあるのか。こうしたことが README、テンプレート、レビュー観点、運用メモとして残っていれば、新しく入ったメンバーも追いやすくなります。

本書を通して扱ってきたのは、コマンドの暗記ではありません。変更を小さく保ち、意図を明確にし、設定で支え、壊しても戻せる形へ流すことです。Git と GitHub は、そのための非常に強い道具です。ここまでの章で見てきた判断が、自分のチームで運用を育てる土台として残れば、本書の目的は果たせたと言えます。
