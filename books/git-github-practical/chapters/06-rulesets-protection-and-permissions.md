# 6章 Rulesets、保護設定、権限設計

チーム開発の運用は、善意だけでは守れません。レビューを通す、main へ直接 push しない、必須チェックを落とさない。こうした原則は重要ですが、口約束だけでは忙しい場面で崩れやすくなります。そこで効くのが GitHub の保護設定です。

以前から protected branches はよく使われてきましたが、現在の GitHub では rulesets を中心に考えたほうが整理しやすい場面が増えています。rulesets は、レビュー、必須チェック、force push 制限、削除制限、対象ブランチの条件などを、より一貫した形で扱えるからです。重要なのは、設定項目の多さではなく、「どの運用ルールを GitHub 側で強制するか」を明確にすることです。

まず入れたいのは、必須レビュー、必須チェック、未解決会話の解決、force push と削除の制限です。これは小規模チームでもかなり効果があります。特に「誰かが急いで main に直接入れてしまう」事故は、運用の善意より設定の強制で防いだほうが安定します。

一方で、設定を厳しくしすぎると運用が止まることもあります。そこで考えるべきなのが例外運用です。誰が bypass できるのか、緊急時にどう記録を残すのか、例外を行使したあとで何を戻すのか。rulesets や保護設定は、設定を入れた瞬間に完成ではなく、例外の扱いまで含めて初めて運用になります。

権限設計も同じです。全員が何でも変更できる状態は、柔軟に見えて実は事故耐性が低いです。逆に権限を厳しくしすぎると、ちょっとした修正でも待ち行列が発生します。重要なのは、履歴を壊し得る操作、保護設定を変えられる操作、リリースを切れる操作のように、影響範囲が大きいものを区別することです。

GitHub の設定を画面の説明として覚える必要はありません。本当に覚えたいのは、「このルールは何を防ぐためにあるのか」です。レビュー漏れを防ぐのか、壊れた CI のまま main に入るのを防ぐのか、誤削除を防ぐのか。その意味が分かっていれば、UI が変わっても運用は崩れにくくなります。

この章で扱った保護設定は、チーム運用の外形です。設定で守れることは設定で守り、人の判断が必要なことだけをレビューや合意形成へ残す。その役割分担ができると、運用はかなり強くなります。rulesets と日常操作の対応をまとめて見たいときは付録 B が役に立ちます。次の章では、その延長として merge queue と CI の実務を見ていきます。
