# 10章 事故対応と復旧

Git と GitHub の運用で、本当に差が出るのは事故のときです。誤ったコミットを main に入れてしまった、タグを打ち間違えた、branch を消してしまった、rebase を共有履歴にかけてしまった。こうした場面で慌てるのは自然ですが、そこで必要なのは高度な操作より、まず状況を切り分けることです。

最初に見るべきなのは、「共有ブランチに影響しているか」です。ローカルだけで壊したのか、すでに他の人が pull できる状態で壊したのかで、選ぶべき操作は大きく変わります。ローカルだけなら `restore` や `reset` で戻せることも多いですが、共有ブランチなら `revert` を優先するほうが安全です。履歴のきれいさより、共同作業者が追えることが大切だからです。

誤 merge や誤 push の初動では、まず被害範囲を確認します。何が main に入ったのか、タグや release まで進んでいるのか、CI はどうなっているのか、他の PR が queue に乗っているのか。ここを見ないまま勢いで歴史を書き換えると、二次被害が広がりやすくなります。

`revert` `restore` `reset` は役割が違います。`revert` は共有履歴上で打ち消すための操作、`restore` は作業ツリーや index を戻すための操作、`reset` は参照の位置そのものを動かす操作です。危険性が高いのは `reset` そのものではなく、共有履歴で何が起きるかを理解せずに使うことです。

タグや releases の事故も軽く見ないほうがよい点です。誤ったタグを公開してしまった場合、コードだけ戻せばよいとは限りません。利用者向けの公開情報、アセット、リリースノートも含めて整合を取り直す必要があります。コードの復旧と、公開情報の復旧は別の作業です。

復旧後に何を残すかも重要です。何が起きたのか、なぜ起きたのか、設定で防げたのか、運用ルールで防げたのか。これを残しておかないと、事故は個人の反省で終わり、次に同じことが起きやすくなります。復旧は、元に戻して終わりではありません。運用を一段強くするまでが復旧です。

この章で大切なのは、事故時の行動を「強い人の手さばき」にしないことです。共有ブランチかどうかを見て、まず `revert` を考え、履歴書き換えは安全域でだけ使い、公開情報も含めて整合を取る。この順番があるだけで、かなり落ち着いて対応できます。代表的な復旧断片は付録 C にまとまっています。次の最終章では、ここまでの運用をどうチームへ定着させるかをまとめます。
