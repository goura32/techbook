# 7章 Merge Queue と CI の実務

チームの変更が増えると、Pull Request がそれぞれ単体では通っていても、main に入る直前の組み合わせで壊れることがあります。レビューは通った、必須チェックもグリーンだった、それでもマージ順によって失敗する。こうした問題に対して効くのが merge queue です。

merge queue の価値は、単に順番待ちを作ることではありません。main に入る直前の組み合わせを、もう一度確かめられることにあります。個々の PR が独立にグリーンであることと、統合直前の状態がグリーンであることは、実務では同じではありません。

GitHub Actions と組み合わせるときに重要なのが `merge_group` です。merge queue を有効にすると、PR 単体のイベントだけではなく、queue 上の統合候補に対して走るワークフローを意識する必要があります。つまり、「PR が通る」だけでなく、「queue に乗った状態でも通る」ことを CI が見られるようにする必要があります。

ただし、merge queue は万能ではありません。直列化されたマージ運用になるため、CI が重いチームでは速度の問題が出ます。したがって、導入前に考えるべきなのは、queue を入れるかどうかだけでなく、何を必須チェックにするか、どこまでを queue 上で再確認するかです。すべてを重い統合テストで塞ぐと、安全にはなっても流量が落ちすぎることがあります。

PR を詰まらせないためには、日常の変更単位も重要です。大きすぎる PR、 flaky なテスト、レビュー待ちの長期化は、そのまま queue の詰まりにつながります。merge queue は最後の安全装置であって、日常の変更設計が悪いとそこだけで救うのは難しくなります。

この章で大切なのは、merge queue を「大規模組織向けの豪華機能」と見ないことです。変更の並列性が増え、main の安定をより強く守りたい場面では、小規模チームでも意味があります。一方で、CI の重さやレビュー速度とのトレードオフもあるため、導入は採用判断として考えるべきです。次の章では、コードの外側にある変更管理として、Issue、Projects、Discussions の使い分けを見ます。
