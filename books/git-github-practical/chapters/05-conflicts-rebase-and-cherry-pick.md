# 5章 競合解消、rebase、cherry-pick の実務

Git の操作で怖がられやすいのが、競合、rebase、cherry-pick です。確かにこれらは履歴を壊しやすい場面でもありますが、危険なのはコマンドそのものではなく、どの場面で使ってよいかを曖昧にしたまま使うことです。

競合そのものは、悪いことではありません。むしろ、同じ場所に複数の変更が集中していることが見えたという意味では、チームの変更圧を教えてくれる信号でもあります。大切なのは、競合を解く前に「どちらが正しいか」ではなく、「最終的にどういう状態にしたいか」を確認することです。競合解消はテキスト編集ではなく、最終仕様の再決定です。

`rebase` は、公開前の履歴を整えたり、main へ追従したりするには有効です。feature branch を最新の main に載せ直し、レビュー前に履歴をきれいにする用途は自然です。しかし公開済みの共有履歴を書き換えると、他の開発者の前提を壊しやすくなります。したがって、`rebase` は「どこまでが自分だけの履歴か」を意識して使うべきです。

`cherry-pick` は、事故対応や hotfix でとても便利です。特定のコミットだけを release branch に持っていきたい、緊急修正だけを main と別系統に反映したい、といった場面では有効です。ただし、コミットの文脈全体を運ぶわけではありません。依存する前後の変更が抜けると、かえって不整合を生むことがあります。だからこそ、`cherry-pick` は便利な近道ではなく、意図を説明しながら使う操作だと考えたほうが安全です。

履歴を書き換えてよい場所と悪い場所をチームで共有しておくことも重要です。ローカルだけの branch、まだ誰にも共有していない branch、レビュー前に整えたい PR などは、比較的自由度が高い場面です。一方で、共有ブランチ、main、他の人が pull 済みの branch では、復旧可能性と追跡可能性が優先されます。その場のきれいさより、共同作業者が混乱しないことを取るべきです。

この章で大事なのは、操作の上手さよりも安全域の理解です。`merge` `rebase` `cherry-pick` `revert` のどれを選ぶかは、履歴の美しさだけでなく、誰がその履歴を見ているかで変わります。付録 C の復旧断片を見返しながら読むと、この線引きがつかみやすくなります。次の章では、こうした判断を GitHub 側の保護設定と権限設計へ接続します。
