## はじめに

Git と GitHub は、開発者にとって最も日常的な道具のひとつです。だからこそ、分かったつもりになりやすい道具でもあります。`commit` できる、`push` できる、Pull Request を作れる。そこまでは多くの人がすぐに覚えます。しかし実務で本当に難しいのは、その先です。変更をどの単位で切るか、レビューしやすい差分とは何か、ブランチをどこまで伸ばしてよいか、設定でどこまで事故を防ぐか、壊したときにどう戻すか。こうした判断は、単なるコマンド知識だけでは身につきません。

本書は、Git と GitHub を「操作手順の集合」としてではなく、「チーム開発の変更管理システム」として捉え直すための本です。履歴、差分、Pull Request、保護設定、merge queue、リリース、事故復旧までを、ばらばらの話としてではなく、ひとつの流れとして扱います。

本書で繰り返し使う視点は、`変更を小さく保ち、意図を明確にし、復旧可能な形で流す` ことです。Git は何でもできる道具ですが、何でもしてよい道具ではありません。共有ブランチで履歴を書き換えるべきでない場面、レビュー前に差分を整える価値、設定で防げる事故、設定では防げない事故。その線引きを言葉にすることが、チームで破綻しにくい運用につながります。

その流れを具体的に追うため、本書では `BeaconBoard` という小さな通しサンプルを使います。`BeaconBoard` は、Web アプリ、API、docs を持つプロダクト用リポジトリです。個人開発から小規模チーム、少し人数が増えたチームまでを想定し、日常開発、レビュー、保護設定、merge queue、リリース、事故対応がどこで効くかを同じ題材で見ていきます。

本書は、Git を初めて触る人の最初の 1 冊ではありません。すでに日常的に Git を使っているが、履歴の切り方やレビューの進め方に自信がない人、GitHub を単なるホスティング以上に活かしたい人、チームの運用が場当たり的で苦しさを感じている人に向けて書いています。読み終えたときに、コマンドの暗記ではなく、変更管理の判断軸が手元に残ることを目指しています。

## 本書の読み方

本書は 1章から順に読むと最も自然につながるように構成しています。特に 1章から5章は、後半の rulesets、merge queue、事故復旧の前提になるため、最初に通して読んでおくと理解しやすくなります。

Git 操作そのものに不安がある読者は、1章から5章を主軸に読むと土台が固まりやすくなります。GitHub の設定や CI との接続が気になる読者は、1章、4章、6章、7章を主軸にするとつながりやすくなります。チーム運用を見直したい読者は、1章から4章と 8章から11章を先に押さえると効果が高くなります。

付録は、本文を補助するために役割を分けています。付録 A は `BeaconBoard` のリポジトリ構成と運用前提、付録 B は主要な Git 操作と GitHub 機能の対応、付録 C は事故復旧や日常運用で見返したい代表断片の確認に向いています。本文を読み進める中で `BeaconBoard` 全体像や操作の位置づけを見失いそうになったら、必要な付録へ戻る使い方が自然です。

また、本書は GitHub の画面を細かく追う本ではありません。GitHub の機能は便利ですが、UI は変わります。本書では、UI の見た目よりも、そこで何を守り、何を防ぎ、何を判断するかを優先します。そのため、章ごとの導入と結論を追いながら、自分のチームへ置き換えて読むほうが効果的です。
