# 2章 Python らしい設計と読みやすさ

Python らしさを語るとき、しばしば「短く書けること」や「ワンライナー」が注目されます。しかし実務で本当に効くのは、短さそのものではありません。読む側が迷わず責務を追えること、値の意味が途中で変わらないこと、例外的な挙動が目立つ場所に置かれていることのほうが重要です。

まず意識したいのは、明示的であることの価値です。Python では動的に属性を増やすことも、辞書へ何でも詰めることも、関数が複数の意味を背負うこともできます。けれども、実務で保守しやすいのは、`何を受け取り、何を返し、どの責務を持つか` が関数名と引数から見えるコードです。1 行でも短くするより、読み手が 1 回で理解できる構造を優先したほうが長く効きます。

`OpsBox` でも、外部 API の辞書をそのまま扱うのではなく、内部では `Job` dataclass を使います。辞書は境界で受け止めるには便利ですが、内部で持ち回るには意味が曖昧です。キーの存在、日時の型、状態の候補、任意項目の扱いが呼び出し側へ漏れてしまうからです。そこで、内部で信頼してよい値は dataclass へ変換し、後続の関数はそれを前提にします。

一方で、何でもクラスにする必要はありません。Python では、振る舞いがほとんどなく、データのまとまりを表したいだけなら dataclass で十分なことが多くあります。逆に、状態のない小さな変換は関数のほうが読みやすいことが多いです。クラスを使うか、モジュール関数を使うかは、拡張性を先回りして決めるよりも、「今ここで何をまとめたいか」で判断したほうが素直です。

資源管理も、Python らしい設計を左右する大きな点です。ファイル、ソケット、データベース接続、ロック。これらは開いて終わりではなく、閉じる責務まで含めて扱う必要があります。`with` 文は単なる構文糖衣ではなく、責務の範囲を明示するための道具です。どこで開き、どこで閉じるかが見えるコードは、障害時の挙動も追いやすくなります。

過剰抽象化にも注意が必要です。Python では、柔らかい言語仕様ゆえに「将来のため」と称して薄いラッパーや抽象基底クラスを増やしやすい傾向があります。しかし実務で最初に必要なのは、変更点を小さく閉じ込めることです。今 1 つしか実装がないなら、まずは 1 つの実装として明確に書き、その実装が痛点になった時点で一般化すれば十分です。

この章で大切なのは、Python らしさを雰囲気で捉えないことです。`短い` `賢い` `魔法っぽい` ではなく、どこに責務があり、どこで値の意味が固まり、どこで例外が目立つか、という観点で見ることです。次の章では、この視点を土台にして、標準ライブラリを実務でどう使い分けるかへ進みます。
