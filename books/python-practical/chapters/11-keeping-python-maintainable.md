# 11章 長く運用する Python コードベース

Python のコードベースは、最初の立ち上がりが速いぶん、運用ルールが後から追いかける形になりやすい傾向があります。スクリプトが増え、実行方法が増え、設定が増え、依存関係が増えた頃になって、ようやく構造を整えたくなる。これは自然な流れですが、そこで必要になるのは大がかりな再設計より、`どこを固定し、どこを変えやすく残すか` の原則です。

まず、ファイル構成と import 境界を早めに整えることが重要です。すべてを `utils.py` や巨大な `main.py` へ寄せるのではなく、内部モデル、設定、外部 API、CLI、集約ロジックのように責務ごとへ分けるだけで、レビューもしやすくなります。Python は import が手軽なため、どこからでも何でも呼べるようになりがちです。だからこそ、物理的に同じパッケージにあることと、設計上近いことは別だと意識する必要があります。

更新ルールも後回しにしないほうがよい点です。Python 本体、`pytest`、配布ツール、型チェック、HTTP クライアント。これらを場当たり的に更新すると、どこで何が壊れたか追いにくくなります。したがって、更新は小さく進める、lockfile を見直す、CI で最低限の品質ゲートを通す、互換性が怪しい変更は先に小さな枝で試す、という流れを決めておくと楽になります。

型とテストの負債も、見て見ぬふりをしないほうがよいです。外部入力を辞書のまま渡している箇所、`Any` や `dict[str, object]` に広く逃がしている箇所、終了コードが曖昧な CLI、設定不足を黙ってデフォルトで飲み込む処理。こうした場所は、後で必ず保守コストとして返ってきます。全部を一度に直す必要はありませんが、どこに負債があり、どこから返すべきかをチームで共有することが大切です。

性能問題も、遅れてからしか見ないと苦しくなります。Python は CPU バウンド処理で不利になることがありますが、実務ではまず I/O、シリアライズ、外部 API 待ち、不要なデータ変換のほうが問題になることが多いです。したがって、最初から「遅い言語だから」と決めつけるより、どこが待ち時間で、どこが変換で、どこが実行環境の問題かを切り分ける姿勢が必要です。

最終的に一番効くのは、チームの共通理解です。Python は自由度が高いため、前提がばらばらだとすぐに書き方が散らかります。どこで dataclass を使うか、設定はどこで読むか、CLI はどう終わるか、依存関係はどう更新するか。こうしたことをすべて厳密な規約にする必要はありませんが、README、テンプレート、レビュー観点、サンプル実装のような形で残しておくと、暗黙知が減ります。

本書を通して扱ってきたのは、派手なテクニックではありません。境界で値を受け止め、内部で意味を安定させ、責務ごとに分け、更新しやすい形で維持することです。Python はその柔軟さゆえに、こうした原則があるだけでぐっと長持ちします。ここまでの章で見てきた設計判断が、自分の現場でコードを育てる土台として残れば、本書の目的は果たせたと言えます。
