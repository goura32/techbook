# 3章 データ構造と標準ライブラリの使いどころ

Python の強みのひとつは、標準ライブラリの厚さです。ファイル処理、時刻、設定、圧縮、サブプロセス、シリアライズ、並行処理まで、実務で必要な基礎の多くを標準だけで扱えます。ここで重要なのは、「標準ライブラリで何ができるか」を暗記することではなく、「どこまで標準で進めると得か」を見極めることです。

まず、ファイルやパスの処理では `pathlib` を土台にするだけで、コードの読みやすさがかなり上がります。文字列連結でパスを作るより、`Path` を使ったほうが、存在確認、拡張子、親ディレクトリ、ファイル読み書きまで一貫した形で扱えます。`OpsBox` でも、設定ファイルやレポート出力先の扱いは `Path` を前提にしたほうが責務が分かりやすくなります。

データの集約には `collections` と `itertools` がよく効きます。手で辞書を初期化してカウントするより `Counter` や `defaultdict` を使ったほうが、何をしたいコードかが見えやすくなります。`OpsBox` の日次レポートで失敗件数や状態別件数を出す処理も、こうした標準ライブラリを使うとビジネスロジックが前面に出ます。

時刻は、Python 実務で特に壊れやすい領域です。`datetime` は便利ですが、naive / aware の違い、タイムゾーン、文字列パース、比較可能性など、細かな前提が多くあります。ここでは `zoneinfo` を含めて、`外部から受け取るときは文字列や時刻の揺れを吸収し、内部では意味を固定する` という考え方を徹底したほうが安全です。日時は値そのもの以上に、どこで確定させるかが大事です。

設定やシリアライズでは、`json` と `tomllib` が土台になります。`OpsBox` でも、API レスポンスのような外部仕様は JSON、アプリケーション設定は TOML と役割を分けると読みやすくなります。ここでも重要なのは、辞書のまま広げないことです。読み込んだ直後のデータは未検証であり、そのまま内部構造の代わりにはなりません。

外部コマンド実行では `subprocess` が標準の中心です。実務でありがちな失敗は、シェルへ丸投げしてしまうことと、失敗時の扱いを曖昧にすることです。`subprocess.run()` で引数を分け、標準出力と終了コードを明示的に扱うほうが、CLI ツールとの接続が安定します。ここでも例外、ログ、設定の話は後続章とつながります。

標準ライブラリを使う価値は、依存を減らすことだけではありません。多くの開発者が知っている前提の上に乗れること、Python の更新と一緒に改善を受けられること、ツールチェーン全体の説明が簡潔になることにもあります。一方で、HTTP クライアントや高度な型チェック、複雑な配布ワークフローのように、標準だけでは不十分な領域もあります。そこでは無理に標準へ閉じ込めるより、役割がはっきりした外部ツールを選ぶほうがよいです。

この章の要点は、標準ライブラリを「何でもできる箱」として見るのではなく、「実務の土台を支える基礎部品」として見ることです。次の章では、その土台の上で型ヒントをどう使い、辞書、dataclass、外部レスポンスの境界をどう設計するかへ進みます。
