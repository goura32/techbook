# 4章 型ヒントと読みやすい API 設計

Python の型ヒントは、TypeScript のように全面的なコンパイル時安全性を与えるものではありません。だからといって価値が薄いわけではありません。実務での型ヒントの主な役割は、`この関数は何を受け取り、何を返すか` を読みやすくし、内部モデルと外部入力の境界を明示することです。

まず大切なのは、型ヒントを入れる場所を選ぶことです。ローカル変数まで何でも細かく注釈するより、公開関数、変換関数、内部モデル、設定、戻り値のように、契約として読む価値が高い場所を優先したほうが効果的です。型ヒントを増やすこと自体が目的ではありません。将来の自分やチームメンバーが、関数の責務を早く理解できるようにすることが目的です。

`OpsBox` では、外部 API から受け取る辞書を `JobPayload` のような `TypedDict` で表し、内部で信頼する構造を `Job` dataclass で表します。この区別はとても重要です。`TypedDict` は外部仕様を説明するには向いていますが、内部で長く持ち回るには向いていません。逆に dataclass は、内部で意味を固定するには向いていますが、未検証の辞書をそのまま押し込むと境界が曖昧になります。

`Protocol` は、振る舞いの契約を表すときに有効です。たとえば「ジョブ一覧を取得できるもの」や「レポートを保存できるもの」のように、具象クラスではなく必要なメソッドだけを示したい場面で役立ちます。ただし、実務では `Protocol` を広げすぎると、抽象化のための抽象化になりやすい点に注意が必要です。まずは具象の責務をきちんと分け、その上で本当に複数実装を入れ替えたいところだけへ使うのが自然です。

戻り値と例外の設計も、型ヒントと深く関わります。`None` を返すのか、例外を送出するのか、空リストを返すのかは、呼び出し側の読みやすさを大きく変えます。`見つからなかった` のような通常フローを例外にしすぎると扱いづらくなりますし、逆に設定不足や認証失敗のような障害を `None` へ押し込むと原因が追いにくくなります。型ヒントは、その判断を呼び出し側へ明示する道具でもあります。

Python 3.14 では annotations の遅延評価が標準になりました。これは 9章でも詳しく扱いますが、型ヒントを積極的に使うコードベースでは影響があり得ます。特に `__annotations__` を直接読んでいるコードや、実行時に注釈を評価する仕組みを入れている場合は、遅延評価を前提に振る舞いを見直す必要があります。ただし、本書の主眼ではありません。ここでは、型ヒントの価値を `静的検査の厳格さ` より `契約の読みやすさ` に置くことで、変化に強い使い方を優先します。

この章での要点は、型ヒントを `全部つけるか、つけないか` で考えないことです。外部入力には `TypedDict`、内部モデルには dataclass、振る舞いの契約には `Protocol` というように、責務に応じて使い分けるほうが実務的です。`OpsBox` の型と関数の対応をまとめて見直したいときは付録 B が役に立ちます。次の章では、その判断を例外、ログ、設定、CLI のような運用に近い入口へ接続します。
