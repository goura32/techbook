# 7章 `pyproject.toml`、依存関係、配布

Python の実務で長く迷いやすいのが、パッケージ管理と配布です。`pip`、`venv`、`poetry`、`uv`、ビルドバックエンド、lockfile。ツール名だけを見ると複雑に見えますが、まず固定したいのは道具ではなく役割です。依存関係の宣言、実行環境の分離、再現性の固定、配布物の生成。この 4 つの役割を分けて考えると、全体像がかなり整理されます。

本書では、`pyproject.toml` を土台に据えます。これは特定ツールの流行に乗るためではなく、Python プロジェクトの中心的な設定点として機能するからです。依存関係、プロジェクトメタデータ、ビルドシステム、ツール設定を、なるべく一か所へ寄せられるメリットは大きいです。`setup.py` や断片的な設定ファイル群より、どこに何が書いてあるかが追いやすくなります。

実行環境の分離には、仮想環境が欠かせません。これは Python に限らず、依存関係が多いエコシステムでは共通の原則です。重要なのは、ローカルと CI の両方で同じ前提を持てることです。`.venv` をプロジェクト単位で持つのか、ツールに管理を委ねるのかは好みやチーム事情もありますが、`どの Python で、どの依存が入っているか` を曖昧にしないことが第一です。

実務例としては `uv` を主例にします。理由は、仮想環境、依存解決、lockfile、Python バージョン管理、ツール実行までをひとつの流れで扱いやすいからです。ただし、本書の主張は `uv` 固有の操作に依存しません。`pyproject.toml` を土台にし、仮想環境を分け、ローカルと CI の再現性を揃える、という原則が先にあります。`pip` と `venv` は、その基礎原則を理解するためにも引き続き重要です。

配布を考えるときも、最初からライブラリ公開を目指す必要はありません。社内ツールや個人ツールでも、`python foo.py` の集合から一歩進めて、`pyproject.toml` に入口を定義し、再現可能なインストール手順を持つだけで扱いやすさは大きく変わります。CLI の入口を明示し、依存関係を宣言し、テストと配布を同じ構造の上へ載せることが、運用可能な Python への大きな一歩です。

依存関係の更新も後回しにしないほうがよい点です。Python 本体、`pytest`、型チェック、配布ツール、HTTP クライアント。これらを一度に大きく更新すると、何が壊れたか追いにくくなります。更新は小さく進め、lockfile と CI で影響範囲を見るほうが安全です。ツールを増やすほど、更新手順も設計の一部になります。

この章の要点は、Python のパッケージ管理を「ツール宗教」の話にしないことです。`pyproject.toml` を中心に据え、仮想環境と再現性を保ち、必要に応じて `uv` のような実務的な道具を使う。その順番で見ると、道具の違いに振り回されにくくなります。設定、CLI、配布の断片をまとめて見たいときは付録 C も参考になります。次の章では、その土台の上で非同期処理と I/O の判断を扱います。
