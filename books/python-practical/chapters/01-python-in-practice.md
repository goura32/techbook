# 1章 Python を実務で使う見取り図

Python は、思いついた処理をすぐに形にしやすい言語です。ファイルを読む、CSV を加工する、HTTP API を呼ぶ、CLI を作る。こうした仕事は驚くほど短いコードで始められます。一方で、実務で苦しくなるのもこの速さの延長です。最初は 1 ファイルだったスクリプトに設定が増え、例外処理が増え、外部 API が増え、テストが必要になったとき、どこまでをそのまま伸ばし、どこから設計を変えるべきかが見えにくくなります。

本書が扱うのは、その「どこから設計を変えるべきか」です。Python の文法だけを知っていても、実務で安全に運用できるコードになるとは限りません。必要なのは、値が不安定な場所と、安定させてよい場所を分けることです。外部 API、環境変数、設定ファイル、CLI 引数、ファイル入力。これらは受け取る側から見ればすべて不安定な入力です。逆に、内部で使う dataclass や小さなサービス関数は、できるだけ安定していてほしい領域です。

この本で繰り返し使う視点は、`境界で疑い、内部で安定させる` ことです。Python は辞書をそのまま渡すことも、`None` をあちこちへ流すことも簡単です。しかしそれを続けると、どの関数が何を期待しているかがすぐに曖昧になります。そこで、外部から入ってくる値は境界で検証し、内部では意味のある dataclass や列挙へ変換し、出力側では必要に応じて再度整形する、という流れを取ります。

この考え方を具体的に追うため、本書では `OpsBox` という小さな通しサンプルを使います。`OpsBox` は、外部サービスからジョブやアラートの情報を取得し、日次レポートを出力する CLI ツールです。次のような構成を前提にします。

- `config.py`: 設定の読み込み
- `models.py`: 内部モデル
- `clients/status_api.py`: 外部 API 境界
- `services/reporting.py`: 集約ロジック
- `cli.py`: 実行入口
- `async_sync.py`: 並列取得

この構成は、複雑さのためではなく責務を見えるようにするためのものです。Python では、1 ファイルに全部書いても動きます。だからこそ、どこを分けると後で楽になるのかを、早い段階で言葉にしておくことが重要です。

Python が特に強いのは、標準ライブラリが豊富で、CLI、ファイル処理、設定、時刻、圧縮、サブプロセス、並行処理まで、かなり多くを標準だけで支えられるところです。逆に、苦手な場面もあります。高い並列性能が要求される CPU バウンド処理、長期に巨大化したコードベースでの暗黙知の温存、外部仕様をそのまま辞書で流し続ける設計などは、放っておくと Python の柔軟さがそのまま弱点になります。

したがって、本書で目指すのは「Python を厳格な言語にする」ことではありません。柔軟さを保ちながら、壊れやすい場所にだけ明示的な構造を入れることです。型ヒントもそのために使いますし、テストもそのために使います。ログや設定、配布や非同期処理も、すべて「長く扱える形にする」ための手段として扱います。

この章では見取り図だけを示しました。`OpsBox` の全体配置を先に見返したいときは付録 A が役に立ちます。次の章からは、Python らしい読みやすさと責務分割の考え方を土台にしながら、標準ライブラリ、型、設定、CLI、テスト、配布、非同期、外部 API 連携へ順に進みます。
