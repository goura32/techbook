# 10章 Web/API 連携と外部サービス境界

Python で実務ツールを書くと、外部 API との接続はほぼ避けて通れません。ジョブ管理、通知、ストレージ、社内サービス。ここで問題になるのは、HTTP クライアントの選び方そのものより、外部仕様をどこで受け止め、どこで内部モデルへ変換するかです。

外部 API のレスポンスは、見た目には JSON で構造化されています。しかし受け取る側から見ると、欠損、追加、型の揺れ、nullable、文字列日時、エラー構造の違いなど、不安定さの塊です。これをそのまま内部で持ち回ると、後続の関数すべてが外部仕様の都合を背負います。そこで `OpsBox` では、`JobPayload` のような生レスポンス表現を境界に置き、`to_job()` で内部 dataclass `Job` へ変換します。

この変換層があると、後続のコードはかなり楽になります。レポート生成は日時が文字列かどうかを気にしなくてよくなり、CLI は欠損キーを直接恐れなくて済みます。つまり、外部 API の揺れを局所化できます。本書で繰り返してきた `境界で疑い、内部で安定させる` という原則が、最も具体的に見えるのがこの章です。

認証、再試行、タイムアウトも、HTTP クライアントの外へ追い出さないほうがよい責務です。ライブラリが提供する機能をそのまま使うことはできますが、プロジェクトとして `どの失敗を再試行し、どの失敗を即座に止めるか` を決める必要があります。タイムアウトも、未設定のまま外部サービスにぶら下がるより、明示的に制約を置くほうが障害時の挙動を追いやすくなります。

同期 API と非同期 API をどう分けるかも設計上のポイントです。非同期クライアントを導入する価値があるのは、複数呼び出しの待ち時間が支配的なときです。単発の CLI 呼び出しや管理系スクリプトでは、同期クライアントのほうが読みやすく保守しやすいことも多いです。重要なのは、ライブラリの機能一覧ではなく、`その処理は本当に並列化の価値があるか` を見極めることです。

観測のしやすさも忘れてはいけません。外部 API 境界は障害点になりやすいので、どの URL へ、どの認証で、どのプロジェクトを取りに行き、何が失敗したかを追える必要があります。ただし、機密値までログへ出すべきではありません。ここでも、`何を残し、何を隠すか` を境界で決めておくことが重要です。

この章で扱った API 連携の考え方は、Python 固有の技巧ではありません。外部仕様をそのまま内部に流さないこと、失敗を観測できるようにすること、同期と非同期を仕事の性質で選ぶこと。こうした判断が、Python の実務コードを長く扱いやすくします。`OpsBox` の変換断片をまとめて見返したいときは付録 C が役に立ちます。次の最終章では、こうした原則をチーム運用と更新ルールまで広げてまとめます。
