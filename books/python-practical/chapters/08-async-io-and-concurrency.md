# 8章 非同期処理と I/O

Python の非同期処理は、導入すると一気に複雑さが増えたように感じやすい領域です。`async` `await` `TaskGroup` `event loop` と新しい用語が増え、同期コードとの接続も気になります。そのため、最初に決めるべきなのは「どう書くか」より「本当に必要か」です。

非同期処理が向いているのは、I/O 待ちが支配的な場面です。複数の API を並列で叩く、大量のネットワーク待ちをさばく、同時に多数の接続を扱う。こうした仕事では、待ち時間を重ねずに進められる価値があります。逆に、CPU を強く使う計算や、小さな CLI の単発処理では、非同期を入れても構造だけが重くなることがあります。

`OpsBox` では、非同期導入の範囲を `複数プロジェクトのデータ取得` に限定します。内部モデルやレポート生成まで全面的に async 化するのではなく、待ち時間がボトルネックになる場所だけへ絞ります。これは、非同期の価値を局所化するためです。Python では、とりあえず async に寄せるより、同期コードの見通しを保ったまま必要部分だけを非同期へ切り出すほうが運用しやすいことが多くあります。

`asyncio.TaskGroup` は、その局所化に役立ちます。複数タスクの生成と待ち合わせを、ひとかたまりの責務として扱えるからです。以前よりも、並列実行の塊を明示的に書きやすくなりました。ただし、並列化しただけで例外やキャンセルが簡単になるわけではありません。どれか 1 つが失敗したときにどう止めるか、タイムアウトをどう扱うか、再試行をどこで行うかは、同期コード以上に明示する必要があります。

同期コードとの接続も重要です。既存のコードベースがほぼ同期で書かれているなら、いきなり全部を書き換えるより、境界で `asyncio.run()` や `asyncio.to_thread()` を使って接続するほうが安全です。非同期に向く場所と、同期のままが読みやすい場所を分けることが、Python では特に大切です。

この章で大切なのは、非同期処理を「現代的だから入れる」ものにしないことです。仕事の性質を見て、待ち時間が支配的で、並列化の価値があり、失敗時の扱いも整理できるところにだけ導入する。それが、長く保守しやすい Python につながります。次の章では、2026年5月13日時点での Python 3.14 の変化を、実務でどう受け止めるかを扱います。
