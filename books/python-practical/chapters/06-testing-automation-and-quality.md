# 6章 テスト、自動化、品質管理

Python では、小さなスクリプトほどテストが後回しになりやすい傾向があります。動いているように見える、実行も速い、手元で試せる。そうした条件が揃っていると、ついテストを省きたくなります。しかし実務では、変更しやすさを支えるのは実行速度ではなく、壊れたときにどこを見るべきかが分かることです。テストはそのためにあります。

まず、テストの層を分けて考えることが大切です。`OpsBox` でいえば、`to_job()` のような変換関数は単体テスト向きです。環境変数と設定ファイルをまとめる `load_settings()` は、ファイルや環境依存を含むので、やや統合寄りのテストが向いています。`main()` のような CLI 入口は、引数と出力を確認するテストが必要です。同じテストでも、何を守るために書くかで粒度が変わります。

本書では `pytest` を主軸にします。理由は、単に人気があるからではありません。assert の素直さ、fixture、`tmp_path`、`monkeypatch`、パラメータ化といった要素が、Python の実務コードと相性がよいからです。特に、設定ファイル、環境変数、一時ディレクトリ、時刻のような「入口の揺れ」をテストしたいとき、`pytest` は必要な道具を過不足なく揃えています。

ただし、テストを増やすこと自体を目的にしないことも重要です。変換関数のように責務が小さい場所は細かく押さえやすい一方で、CLI のすべてのメッセージやログの細かな文面まで固定すると、変更コストが上がります。テストで守るべきなのは、仕様と運用の前提です。たとえば「失敗時に非ゼロの終了コードを返す」「設定不足なら明示的に失敗する」「生レスポンスの欠損キーで誤った内部モデルを作らない」といった点です。

自動化と品質管理も、テストだけでは完結しません。静的検査、フォーマット、型チェック、最小限のスモークテストをどう組み合わせるかが重要です。Python は柔軟なので、静的検査だけでは防げないことも多いですし、逆に実行テストだけでは読みやすさの劣化を防ぎきれないこともあります。そこで、`pytest`、型チェック、Lint、フォーマットの責務を分けて考えたほうが、ツールチェーン全体が理解しやすくなります。

良いテストは、コードの正しさだけでなく、設計の歪みも教えてくれます。テストしづらいコードは、たいてい責務が大きすぎるか、外部入力への依存が深すぎます。`load_settings()` が環境変数とファイル読込と API 初期化まで抱え始めたら、それはテストの難しさとして表面化します。テストは品質の最後の砦であると同時に、構造の歪みを早く知らせるセンサーでもあります。

次の章では、こうして育てたコードを、`pyproject.toml` と依存関係管理の土台の上へどう載せるかを扱います。
