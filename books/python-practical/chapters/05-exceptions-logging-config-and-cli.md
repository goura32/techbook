# 5章 例外、ログ、設定、CLI

実務の Python コードで壊れやすいのは、ビジネスロジックそのものよりも、その周辺です。設定をどこで読むか、例外をどこで止めるか、ログをどこで書くか、CLI から何を受け取るか。こうした入口の設計が曖昧だと、小さなツールでもすぐに運用しづらくなります。

まず、例外を握りつぶさないことが重要です。Python では `try/except Exception` を簡単に書けるため、失敗を「とりあえず飲み込む」コードが増えやすい傾向があります。しかし実務では、どの失敗が想定内で、どの失敗が異常かを分ける必要があります。設定不足、認証失敗、外部 API の一時障害、予期しないレスポンス。これらを同じ `None` や同じ警告ログで済ませると、運用時に原因を追えません。

次に、ログは print の延長ではありません。print は開発中の観察には役立ちますが、運用上の記録としては、時刻、レベル、文脈、出力先の制御が不足します。`logging` を使う理由は、見た目を整えることではなく、障害時に `何が起きたか` を後から追えるようにすることです。特に CLI ツールでは、標準出力に業務結果、標準エラーやログに運用情報を分けるだけで、後続の自動化がかなり安定します。

設定の扱いも、入口設計の要です。環境変数、設定ファイル、CLI 引数はすべて外部入力ですが、役割は同じではありません。環境変数は機密値や実行環境依存の値、設定ファイルは繰り返し使う既定値、CLI 引数はその実行だけで変えたい値、というように責務を分けると混乱が減ります。`OpsBox` では `load_settings()` を境界に置き、環境変数と TOML 設定をまとめて `OpsBoxSettings` に変換します。

CLI 設計では、`argparse` を土台にするだけでかなり十分です。実務で重要なのは、引数解析ライブラリの華やかさより、引数が設定やサービス呼び出しとどうつながるかです。`main()` がやるべきことは多くありません。引数を読む、設定を読む、サービスを呼ぶ、結果を出力する、終了コードを返す。この責務を越えて、外部レスポンスの整形や設定の細かな解釈まで持ち始めると、CLI 自体が重くなります。

終了コードも軽く見ないほうがよい点です。人が見るときはメッセージだけで十分でも、CI や cron、シェルスクリプトは終了コードで成功失敗を判断します。したがって、エラーを起こしたときに例外をどこで受け、どの終了コードへ変換するかを決めておく必要があります。ログと終了コードが分かれている CLI は、それだけで運用へ載せやすくなります。

この章で扱った例外、ログ、設定、CLI は、いずれも `入口` の設計です。ここを早い段階で整えると、後のテスト、配布、非同期化もぐっと楽になります。次の章では、その入口と内部ロジックを支えるテストと品質管理へ進みます。
