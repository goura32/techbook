## はじめに

Python は、書き始めるまでの速さで選ばれることが多い言語です。ちょっとした自動化、ファイル処理、API 呼び出し、データ変換。そうした仕事をすぐに形にできることは大きな魅力です。しかし実務では、その「すぐに書ける」がそのまま「長く運用できる」にはつながりません。設定が散らばり、例外処理が場当たり的になり、依存関係の管理が曖昧なままスクリプトが増えていくと、Python の速さはやがて保守の難しさに変わります。

本書は、Python を便利スクリプトのための言語としてではなく、長く保守できる実務基盤として使うための本です。文法や小技を網羅することよりも、どこで型を使うか、どこで例外を止めるか、どこで外部入力を疑うか、どこまで標準ライブラリで進めるか、といった判断を一貫した視点で整理することを重視します。

本書で繰り返し使う中心的な視点は、`境界で疑い、内部で安定させる` ことです。Python は柔軟で、辞書も文字列も例外も簡単に流せます。だからこそ、外部 API、設定ファイル、環境変数、CLI 引数のような不安定な入力をどこで受け止め、どの段階で内部モデルへ変換するかが重要になります。この視点は、型ヒント、例外設計、標準ライブラリ、非同期処理、テスト、配布まで、すべての章を貫きます。

その流れを具体的に追えるようにするため、本書では `OpsBox` という小さな通しサンプルを使います。`OpsBox` は、外部サービスからジョブやアラートの情報を取得し、内部モデルへ正規化し、CLI でレポートを出力するツールです。完成品を見せるための題材ではなく、Python のコードがどこで壊れやすく、どこで安定させるべきかを同じ題材で追うための土台として使います。

本書は、Python を学び直したい人のためだけの本ではありません。Python を日常的に使っているが、設計や運用が手元で曖昧になっている人、他言語経験はあるが Python の流儀と実務の勘所を整理したい人、小さなスクリプトをチームで保守できるツールへ育てたい人に向けて書いています。読み終えたときに、便利なモジュール名だけでなく、「どこで何を固定し、どこで何を逃がすか」という判断軸が残ることを目指しています。

## 本書の読み方

本書は 1章から順に読むと最も自然につながるように構成しています。特に 1章から5章は、後半の前提になるため、最初に通して読んでおくと理解しやすくなります。

CLI や自動化スクリプトの関心が強い読者は、1章から7章を主軸に読むと本書の価値が伝わりやすくなります。API 連携やバッチ処理の関心が強い読者は、1章から5章、8章、10章を主軸にするとつながりやすくなります。チーム運用や保守性の観点から読みたい読者は、1章から6章と11章を先に押さえるのがおすすめです。

付録は、本文を補助するために役割を分けています。付録 A は `OpsBox` の構造、付録 B は型と関数の対応、付録 C は代表コード断片の確認に向いています。本文で `OpsBox` 全体像を見失いそうになったときや、特定の型や関数がどこで登場したかを振り返りたいときに使うのが自然です。

また、本書は特定フレームワークや特定ライブラリの使い方に寄りすぎないようにしています。標準ライブラリを土台にしつつ、`pytest` や `uv` のように実務で強く効く周辺ツールだけを選んで扱います。そのため、個別ツールの細かなオプションを覚える読み方よりも、章ごとの導入と結論を追いながら、自分の現場の構成へ置き換えて読むほうが効果的です。
