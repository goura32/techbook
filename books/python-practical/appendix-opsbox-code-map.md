# Appendix B. OpsBox のコードマップ

## この付録の役割

この付録は、本文に登場した主要な型と関数を、`OpsBox` 全体の流れの中で見直すためのものです。本文では章ごとに必要な断片だけを示しているため、読後に「`load_settings()` はどこで使われていたか」「外部 API の辞書と内部モデルの違いは何だったか」をまとめて確認したくなる場面があります。

## まず全体の流れを見る

`OpsBox` のコードは、大きく見ると次の流れでつながります。

1. 設定を読む
2. 外部 API から生データを受ける
3. 生データを内部モデルへ変換する
4. レポートや CLI 出力へ加工する
5. 必要に応じて非同期でまとめて取得する

本書で繰り返してきた `境界 -> 検証 -> 内部モデル -> 利用` という流れを、`OpsBox` の型と関数に落とすと次のようになります。

- 外部 API: `JobPayload`
- 境界での変換: `to_job()`
- 内部で信頼する型: `Job`
- 実行環境の設定: `OpsBoxSettings`
- CLI 向け集約: `DailyReport`

## 主要な型

### `JobStatus`

- 登場章: 2章
- 役割: ジョブ状態の列挙

`JobStatus` は、小さな型ですが本書全体の考え方をよく表しています。文字列の自由入力をそのまま許さず、内部で扱う選択肢を固定することで、後段の条件分岐と出力を安定させます。

### `Job`

- 登場章: 2章, 4章, 10章
- 役割: 内部で信頼する dataclass

`Job` は `OpsBox` の中心にある内部モデルです。CLI もレポート生成も、外部レスポンス辞書ではなくこの dataclass を扱います。

### `JobPayload`

- 登場章: 4章, 10章
- 役割: 外部 API の生レスポンス

`JobPayload` は `TypedDict` で表される生データです。キー名、nullable な値、文字列の日時など、外部仕様の都合をそのまま持っています。

### `OpsBoxSettings`

- 登場章: 5章, 7章
- 役割: 実行環境を表す設定

環境変数や設定ファイルをそのまま引き回さず、`OpsBoxSettings` へ一度まとめることで、CLI とサービス層の境界を明確にします。

### `DailyReport`

- 登場章: 5章, 10章
- 役割: 出力向けに整えた集約結果

`DailyReport` は画面モデルではありませんが、内部モデルをそのまま出力へ流さないという点では同じ役割です。

## 主要な関数

### `load_settings()`

- 登場章: 5章, 7章
- 役割: 環境変数と設定ファイルから `OpsBoxSettings` を組み立てる

### `to_job()`

- 登場章: 4章, 10章
- 役割: 生レスポンスを `Job` へ変換する

`to_job()` は、`OpsBox` の変換層を代表する関数です。外部 API の辞書をそのまま通さず、日時や状態、任意項目を内部で扱いやすい形へ整えます。

### `fetch_jobs()`

- 登場章: 4章, 10章
- 役割: API からデータを取得し、`Job` の列を返す

### `build_daily_report()`

- 登場章: 3章, 5章, 10章
- 役割: `Job` の列から出力向けの集約を組み立てる

### `sync_projects()`

- 登場章: 8章
- 役割: 複数プロジェクトのデータを非同期で取得する

## 最後に見るべきこと

`OpsBox` の付録で本当に持ち帰ってほしいのは、個々の型名や関数名ではありません。次の流れが 1 冊を通して繰り返されていたことです。

- 外部入力をそのまま流さない
- 境界で検証する
- 内部モデルを安定させる
- 利用側の責務に合わせて再度変換する

`OpsBox` は小さな例ですが、この流れは実務の Python でもかなりそのまま使えます。
