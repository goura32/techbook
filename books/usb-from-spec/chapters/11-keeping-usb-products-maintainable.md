# 11章 長く保守できる USB 製品設計

USB 製品を一度動かすことと、長く保守できる状態にすることは別です。最初の試作では動いたとしても、host OS が変わり、ケーブルの種類が増え、power condition が変わり、将来の規格改訂が入ると、最初に曖昧だった部分が必ず効いてきます。だから USB は、完成した瞬間ではなく、変化したあとにどれだけ説明できるかで設計の良し悪しが見えます。

長期保守で最初に効くのは、全部を一度に実装しないことです。Type-C だから全部の mode を積む、PD があるから最初から高電力を前提にする、複数 class を全部同時に公開する。こうした構成は最初から組み合わせ爆発を招きます。最小構成を明確にし、拡張点を後から足せるようにしておくほうが、結果的に速く安全です。

ここでの「最小構成」は、機能削減のためではありません。何がなくても成立すべきかを先に決めるためです。USB 製品の保守で苦しくなるのは、最低限の成立条件が不明なまま機能が増えたときです。`TraceDock` なら「まず列挙する」「制御経路が開ける」「ログは次段階」「高負荷モードは最後」という順番があります。この順番があるだけで、改修や不具合対応のたびに戻る場所ができます。

host 側と device 側の責務分離も重要です。device が決めること、host tool が決めること、OS へ任せることを混ぜると、障害時に説明責任の場所が曖昧になります。`TraceDock` でも、制御、ログ、電力の責務を分けることで、どこを変えればどこへ影響するかを追いやすくしています。

この責務分離は、コード構造だけでなくドキュメント構造にも効きます。descriptor の変更履歴、cable 条件、動作確認した host controller、PD 条件。こうした情報が散らばっていると、保守は一気に重くなります。商用製品では、ソースコードだけでなく「どの前提で動くのか」を継続的に更新できるかが重要です。

ケーブル依存、OS 依存、電力依存を見える形で残すことも欠かせません。USB の問題は再現条件に依存するので、サポートや保守の現場では「どの cable で、どの host で、どの電力条件か」がとても重要です。これはコードの話ではありませんが、USB 製品を保守するうえではコードと同じくらい重要な情報です。

実務では、少なくとも次の情報を最初から残すと保守しやすくなります。

- 動作確認した cable 条件
- hub 経由の可否
- host OS と controller の組み合わせ
- default power だけで成立する機能
- PD 契約が必要な機能

この一覧があるだけで、field からの問い合わせに対して「何が仕様で、何が未確認か」をかなり明確に返せます。

仕様更新への追従も、改訂版を全部追うことではありません。自分の製品に効く改訂が何かを見極めることです。Document Library には USB 2.0、Type-C、PD、USB4 の更新が並んでいます。全部を同じ温度で追うのではなく、どの層が自分の製品に関係するかを見続けるほうが実務的です。

追従の仕方としても、全改訂を追うのではなく、「自分の製品が依存している層」に監視対象を絞ると続けやすくなります。Type-C を採用しているなら connector と cable 条件、PD を使っているなら power contract、USB 3.x を使っているなら高速 path と interop。こうして分けると、規格更新が巨大な負担ではなく、保守の routine に近づきます。

最後に、USB を選ばない判断も持っておくとよいです。USB は便利ですが、常に最良ではありません。単純なデバッグポート、専用高速リンク、別の電力設計が向くこともあります。USB を深く理解することの価値は、USB を何にでも使うことではなく、USB を使うべき場面とそうでない場面を分けられることにあります。

この章の結論は、USB の保守性は仕様知識の量だけでは決まらないということです。どの層を分けて設計したか、どの観測点を最初から持ったか、どの条件を記録したかが長く効きます。USB を深く理解することは、複雑さを増やすためではなく、複雑さを制御するためにあります。
