# 6章 電力供給、USB PD、役割交渉

USB を「データ転送の規格」としてだけ見ていると、USB Power Delivery の重要性を見落としやすくなります。現在の USB は、多くの場面で電力供給の規格でもあります。そしてこの軸は、列挙や転送とは別に考えなければなりません。データが通ることと、必要な電力契約が成立していることは同じではないからです。

USB PD を理解するときの最初の鍵は、power role と data role を混同しないことです。host/device と source/sink は、しばしば同じように扱われますが、実際には別の軸です。Type-C の世界では、データ側では device でも、電力側では source になることがあります。ここを切り分けて見られないと、設計も debug も不安定になります。

USB-IF の公開情報を見ると、USB Power Delivery は USB PD Revision 3.2 Version 1.2 まで進んでおり、技術ページでは 240W までの power delivery を説明しています。つまり、現代の USB では「どれだけ速くデータを流せるか」と同じくらい、「どの契約でどれだけ電力を扱えるか」が重要です。

ここで大切なのは、Type-C と PD の関係を「密接だが同一ではない」と理解することです。Type-C は connector と role signaling の土台であり、PD はその上でどの電力契約を結ぶかを扱います。したがって、Type-C で attach しても PD 契約が成立していないことは普通にありますし、PD 契約がなくても USB device として列挙することはあります。この切り分けがないと、「Type-C で挿したのに高機能モードへ入らない」現象を正しく説明できません。

`TraceDock` のような device で考えると、電力設計は次の 3 段階に分けると整理しやすくなります。

- 最低限の既定電力で成立すべき機能
  - attach、enumeration、基本的な HID control
- PD 契約があると安定する機能
  - 長時間ログ取得
  - 高サンプリング動作
- PD 契約がないと提供しない機能
  - 追加センサー駆動
  - 高負荷な後処理

この分離をしておくと、PD 契約が落ちたときに device 全体が壊れるのではなく、「どの機能を縮退運転へ落とすか」を決めやすくなります。商用製品では、ここが設計のわかりやすさに直結します。

`TraceDock` では、通常動作は既定の USB 電力で足りる前提にし、追加機能が必要なときだけ PD 契約で拡張する考え方を取ります。ここで学びたいのは、最初から高電力前提にしないほうが設計が分かりやすいということです。まず最小の power budget で成立させ、必要な機能だけを PD へ載せるほうが安全です。

power role と data role を切り分ける価値は、実装時だけでなく debug 時にも大きいです。たとえば「device として見えているのに期待したサンプリング周波数へ上がらない」という現象では、data role 側は正しくても power role 側で十分な契約が取れていない可能性があります。逆に、PD 契約があるからといって data role 側の列挙や driver 問題が片付くわけでもありません。両者は同じ cable の中にあっても、別々に壊れます。

PD 交渉の失敗パターンも、いくつかの典型へ分けられます。

- attach はするが既定電力のまま:
  - cable capability
  - source 側 policy
  - sink 側 request 条件
- 一度は高電力へ上がるが不安定:
  - 電力変動
  - 熱条件
  - cable quality
- 高機能モードへ入る前に reset がかかる:
  - source/sink role の切替条件
  - firmware 側の state machine

こうした失敗では、enumeration ログだけ見ていても原因が見えにくいことがあります。むしろ「attach はしている」「descriptor も読めている」「しかし power contract が不足している」という状態を認識できるかどうかが重要です。ここで power trace や PD log が効きます。

電力交渉の失敗も、よくある USB トラブルのひとつです。Type-C でつながっている、でも期待したモードに入らない。これは firmware バグだけでなく、cable capability や PD 契約不成立、power role の想定違いで起きます。だから debug のときも、enumeration より前に power contract を見る場面があります。

実装側では、「どの contract があればどの機能を有効化するか」を明示しておくと、仕様と firmware が結びつきます。host 側や test 側では、「どの power condition で再現したか」を記録しておくと、再現性の低い不具合を減らせます。USB PD を別軸として扱うというのは、単に知識を増やすことではなく、観測点を増やすことです。

この章の結論は、USB PD は高電力のおまけではなく、USB を理解する別軸の仕様だということです。Type-C の話と同時に出てきやすいですが、役割は違います。次の章では、USB 2.0、USB 3.2、USB4 の関係を整理し、「同じ USB なのに何が違うのか」を marketing 名から切り離して見ていきます。
