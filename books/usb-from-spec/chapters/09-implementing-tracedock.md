# 9章 `TraceDock` を実装視点で読む

ここまでの章で、USB の各層を分けて見てきました。この章では、それらを `TraceDock` というひとつの device へ戻します。目的は、USB の仕様要素がどこで実装判断に変わるかを確認することです。descriptor、transfer、Type-C、PD、host tool は、ばらばらの話ではありません。

まず重要なのは、`TraceDock` に載せる機能を最初から増やしすぎないことです。USB 製品は、できることを増やすほど debug の組み合わせが増えます。だからこそ `TraceDock` では、制御は HID、ログは bulk、電力は最小構成で始め、必要なときだけ PD へ広げるという分割を取ります。これは仕様の縮小ではなく、運用可能な構成へ寄せるための設計です。

この設計を具体化すると、`TraceDock` は次のような責務分割になります。

- 最低限の起動と列挙:
  - 既定電力だけで成立させる
- 制御経路:
  - HID control interface で mode 切替と状態確認を行う
- ログ経路:
  - bulk transfer でまとまったデータを流す
- 拡張機能:
  - PD 契約成立時だけ有効にする

こうしておくと、「何がなくても最低限動くべきか」が先に決まります。USB 製品の設計でつらいのは、すべての機能が同じ重要度で見える状態です。最低限の列挙と制御、追加的なログ取得、さらにその上の高負荷機能、と段を分けるだけで判断はかなり楽になります。

descriptor の設計も、そのまま host 側 UX に効きます。device 全体を vendor-specific に閉じるより、制御しやすい部分は標準的な class へ寄せたほうが、host 側の取り回しが楽です。一方で、無理に全部を標準 class へ押し込むと、device 側の設計が不自然になることもあります。大切なのは「何を host へ分かりやすく見せたいか」を先に決めることです。

`TraceDock` では、最初に host 側の使い方から逆算します。

- 最初にやりたいこと:
  - device を見つける
  - 状態を読む
  - mode を切り替える
- 次にやりたいこと:
  - ログをまとまって取る
  - 不具合時に転送経路を切り分ける

この順で考えると、制御経路とログ経路を分ける合理性が見えてきます。単一 interface にまとめると device 側は簡単に見えますが、host 側では「最初にどこへ触ればよいか」が曖昧になります。

電力設計でも同じことが言えます。Type-C を使うからといって、最初から高電力前提にしないほうが構造は分かりやすくなります。通常動作を既定電力で成立させ、追加機能だけを PD 契約に乗せるほうが、異常時の切り分けも簡単です。つながったが高機能モードに入らない、という現象も、この分離があれば観測点を持ちやすくなります。

商用製品として見ると、この分離は support のしやすさにもつながります。たとえば field で「高負荷測定モードに入らない」という報告が来たとき、既定電力動作の制御経路が正常なら、問題を PD 条件や cable へかなり絞れます。反対に、最初から全部が高電力前提だと、attach しているのに何もできない、という重い失敗になりがちです。

host 側ツールの責務も明確にしておきます。descriptor を読む、device を識別する、制御 interface を開く、bulk logging を受ける、必要なら firmware update を行う。全部をひとつの大きなツールへ押し込むより、debug 用と通常運用用で責務を分けたほうが保守しやすいこともあります。

host 側では、少なくとも次の 3 層に分けておくと扱いやすくなります。

- enumeration / identification 層
  - 何がつながっているかを見る
- control 層
  - 設定変更や状態取得を行う
- capture / logging 層
  - 継続データを扱う

この分離は code structure のためだけでなく、debug 手順のためでもあります。capture が壊れていても identification と control が生きていれば、観測を続けやすいからです。

`TraceDock` の設計から得たい教訓は、「USB の仕様要素を全部実装へ写す」のではなく、「仕様要素をどの責務へ割り当てるかを先に決める」ことです。descriptor は host への契約、transfer type は経路の契約、PD は power 条件の契約です。これらを一枚の構成図で見られるようにしておくと、製品が育っても破綻しにくくなります。

付録 A は、この章で特に役に立ちます。`TraceDock` の全体配置を見失ったときに戻る場所として使ってください。次の章では、こうして組んだ device を実際にどう解析し、どこまで analyzer や compliance 文書が必要になるかを整理します。
