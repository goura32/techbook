# 12章 実装・解析・長期保守

USB 製品を一度動かすことと、長く保守できる状態にすることは別です。host OS が変わり、ケーブルの種類が増え、PD 条件が変わり、dock や display の組み合わせが増えると、最初に曖昧だった部分が必ず効いてきます。だから USB の設計は、完成した瞬間ではなく、変化したあとにどれだけ説明できるかで良し悪しが見えます。

## 12-1. 最小成立構成を先に決める

全部を一度に実装しないことは、USB でも非常に重要です。まず列挙する、次に最低限の制御ができる、次に主要データ経路が動く、そのあとに高負荷モードや拡張機能を足す。この順番があるだけで、改修や不具合対応のたびに戻る場所ができます。

## 12-2. host 側と device 側の責務分離

device が決めること、host tool が決めること、OS へ任せることを混ぜると、障害時に説明責任の場所が曖昧になります。descriptor、class、power 条件、controller の status、OS の見え方を別々に残しておくと、どこを変えればどこへ影響するかを追いやすくなります。

特に USB Type-C と PD を含む製品では、`MCU firmware の責務` `PD controller が自律的に持つ状態` `OS や driver が判断すること` を分けて記録しておく価値があります。ここが曖昧だと、attach しない問題も、contract しない問題も、映像が出ない問題も全部 firmware 側の話として押し込まれてしまいます。責務を分けて残すこと自体が保守性です。

## 12-3. cable、OS、power 条件を記録する

USB の問題は再現条件に依存するので、コードと同じくらい `環境情報` が重要です。少なくとも、

- 動作確認した cable 条件
- hub / dock 経由の可否
- host OS と controller の組み合わせ
- default power だけで成立する機能
- PD contract が必要な機能

は最初から残したほうが保守しやすくなります。

## 12-4. 規格更新をどう監視するか

改訂版を全部追うことが目的ではありません。自分の製品に効く改訂を見極めることが大切です。Type-C を採用しているなら connector と cable 条件、PD を使っているなら power contract と controller 状態、USB4 や Alt Mode を使っているなら dock / cable / display との相互作用を優先して監視するほうが実務的です。

言い換えると、監視対象は仕様書そのものではなく `自分の失敗モードに効く差分` です。HID 入力機器なら class や report の扱い、高速 storage なら cable や host controller 条件、映像付き dock なら Alt Mode や PD、USB4 discovery の更新が効きます。製品の主機能と故障しやすい層を結びつけて監視するほうが、改訂情報を現場価値へ変えやすくなります。

## 12-5. USB を選ばない判断

USB は便利ですが、常に最良ではありません。単純な debug port、専用高速リンク、別の電力設計が向くこともあります。USB を深く理解する価値は、何にでも USB を使うことではなく、USB を使うべき場面とそうでない場面を分けられることにあります。

## 12-6. 仕様を現場価値へ変える

本書を通して見てきたのは、`仕様を知っている` ことそのものではなく、`仕様をどう観測と判断へ変えるか` でした。USB 2.0 の列挙、descriptor、class、USB 3.2 の高速側、Type-C の配線、PD controller の状態、USB4 と Alt Mode の境界。これらを別々に見られるようになれば、USB は一気に扱いやすくなります。

この章の結論は、USB の保守性は仕様知識の量だけでは決まらないということです。どの層を分けて設計したか、どの観測点を最初から持ったか、どの条件を記録したかが長く効きます。USB を深く理解することは、複雑さを増やすためではなく、複雑さを制御するためにあります。

現場で最後に効くのは、`原因を 1 回で言い当てる力` よりも、`どの順で切り分ければ再現性のある説明になるか` を持っていることです。USB は複数仕様の重なりだからこそ、説明の順番がそのまま品質になります。本書がその順番を作る助けになれば、この巻の役割は十分に果たせています。
